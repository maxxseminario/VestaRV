X2 Zabha rd-aliasing negative controls (F1 + F2)
================================================

Two seeds, each a one-hunk REVERT of an X2-F1/F2 fix (commit 8eb6028). They
re-introduce the rd-aliasing faults the gate review caught (the historical
no-operand-latch class: LIVE regfile read ports used where an alias-proof
REGISTERED copy is required).

  x2_zabha_alias_f1.patch  (hdl/common/vesta/vesta.vhd)
      amo_wen keys off the LIVE rs1 port (rs1_value = datapath src_a) instead of
      the registered amo_addr_reg(1:0). Because rd is written in AMO_WRITEBACK
      (two states before AMO_WRITE), a rd==rs1 sub-word AMO sees the sign-extended
      old memory value on rs1 and selects the WRONG byte lane.
      DETECTOR: extzabha ON aliasing arm `amoswap.b rd==rs1` (lane 1: old byte
      0xBB -> rs1 becomes 0xFFFFFFBB -> lane (0xBB&3)=3 written, guard mismatch).

  x2_zabha_alias_f2.patch  (hdl/common/vesta/datapath.vhd)
      amo_b_ext (the AMO compute operand) reads the LIVE rs2 port
      (write_data_reg_val) instead of the registered amo_rs2_reg. A rd==rs2 AMO
      computes with the clobbered operand. This is the PRE-EXISTING word-AMO fault
      (amoadd.w a0,a0,(a1)); the byte/half path inherited it.
      DETECTOR: rv32ua/amoalias.S `amoadd.w rd==rs2` / `amoswap.w rd==rs2`
      (DEFAULT build) and extzabha ON `amoadd.b rd==rs2`.

M8 DISCIPLINE (the code was the seed): the aliasing tests were written and run
against the PARENT commit (402d2d9/d506f32, both faults present) BEFORE the fix.
Recorded there: amoalias FAIL (word rd==rs2), extzabha ON FAIL (sub-word F1+F2).
After the fix (8eb6028) both PASS; word-AMO regression clean.
