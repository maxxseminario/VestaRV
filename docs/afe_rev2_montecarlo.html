1 · Two decisions that make or break the run

1.1 Run MC on a closed-loop bench, never on an open-loop one

The verification plan specifies a1_mc as "Monte Carlo mismatch, 200 pts, on the a1_loop setup". Do not do this. The open-loop bench (TypOpenLoopWBiasTB) holds its operating point only because V_InDCOffset is hand-set to cancel the nominal offset (−61 µV). With Aol ≈ 8800, the output stays off the rails only while the residual offset is under roughly 115 µV — and the mismatch spread being measured is ±5 mV. Essentially every one of the 200 samples would slam to a supply rail and the run would return noise.

Rule. Monte Carlo needs a bench whose operating point is valid for every sample. A unity-gain buffer self-biases — the loop forces vout = vcm + Vos whatever Vos happens to be — so the buffer harness (DriveWBiasTB / UnityFeedbackWBiasTB) is the correct host for any offset or mismatch measurement. The same reasoning kills any scheme that "calibrates" the offset in a prior test and feeds it forward with calcVal: every MC draw has a different offset, so a single calibrated scalar is correct for one sample and wrong for the other 199 — and nulling the offset defeats the measurement anyway.

1.2 The four model-section families are not interchangeable

Mismatch statistics do not live in the mc_* sections, the mc_* sections cannot vary anything on their own, and neither of them declares the parameters the other one needs. Getting this wrong produces either a clean-looking run with σ = 0 or a wall of SFE-1996 errors, depending on which half you got wrong. See §2.

2 · Model sections — the silent-zero trap

In crn65gplus_2d5_lk_v1d0.scs the families split four ways, not three. Every line number below is in that file, PDK as installed at /opt/design_kits/TSMC65-PDK:

Section familyWhat it isDeclares…Has a statistics block?
tt_25, ss_25, ff_25, sf_25, fs_25 (13655…) Fixed process corners. Include mos_25. parn1_25…parp2_25 = 0 — the mismatch parametersNo
mc_25 (9485), mc_res (112434), mc_mim (114308) Process variation — model parameters written as functions of par6/par7/par8 (MOS) and par1_res…par4_res. Also include mos_25. nothing for mismatch — no parn*_25 at all No

stat_mis_25 (8172), stat_mis_res (625), stat_mis_mim (598) Mismatch statistics nothing — only vary statementsYes — mismatch
The consequence, and it is not obvious: mc_25 and tt_25 are not a drop-in swap. mc_25 includes the same mos_25 model cards, whose temp1=parn1_25 temp2=parn2_25 expressions need the mismatch parameters — but only the fixed-corner sections declare them. So mc_25 + stat_mis_25 dies, and tt_25 + mc_25 together die too (duplicate noiseflag_25, par_res, … → SFE-59). §2.2 gives the row set that works.

The whole of stat_mis_25 is this:

statistics {
  mismatch {
    vary parn1_25 dist=gauss std=1/1
    vary parn2_25 dist=gauss std=1/1
    vary parp1_25 dist=gauss std=1/1
    vary parp2_25 dist=gauss std=1/1
  }
}

Those four parameters are declared in tt_25, consumed by the mos_25 device equations, gated by the per-instance mismatchflag, and varied only when stat_mis_25 is also present. All three pieces are mandatory.

If you select a stat_mis_* row and no montecarlo statement, Spectre runs 200 identical samples and reports σ = 0. Nothing warns you. And a mc_* row on its own varies nothing either — the randomN parameters it depends on are declared and varied in stat, a section with a confusingly similar name that the earlier revision of this note did not mention.

2.2 Model library rows for a process + mismatch MC

Correction, 2026-07-26. This section previously said: "swap the three process rows to mc_25 / mc_res / mc_mim and keep the stat_mis_* rows." That does not run. Verified in batch Spectre 20.1: it aborts during hierarchy flattening with dozens of ERROR (SFE-1996): 'a1_25': Unknown parameter 'par6' plus ERROR (SFE-12): invalid parameter 'parn1_25' … in the 'mismatch' block. Two things were missing — the stat/stat_res/stat_mim process-statistics rows, and a declaration of the four MOS mismatch parameters that only the fixed-corner sections provide.

Ten rows. Nine sections of the master file, plus one two-line local definitions file:

There is no tt_25 / tt_res / tt_mim row in this list. Including them alongside the mc_* rows is the SFE-59 duplicate-parameter failure (noiseflag_25, par_res, …) and cannot be made to work by reordering.

Row 1 is section mos_mis_params_25 of castalia/ic/models/castalia_mc_models.scs, which is just this:

section mos_mis_params_25
    parameters parn1_25=0 parn2_25=0 parp1_25=0 parp2_25=0
endsection mos_mis_params_25
It is wrapped in a named section deliberately: a corner's Model Files table requires a section name, so the sectioned form is the only one legal in both places (§2.4). Row order does not matter — verified with it first and last; Spectre resolves the parameter namespace after parsing all includes.

2.2.1 If you are starting from the imported tsmcN65_typ_* corner (you are)

The tables above are the minimal row sets. In practice the MC test inherits the imported corner's full family sweep — 46 tt_* rows plus the three stat_mis_* rows, 49 in total. Do not delete the other 43. Swap only the families the DUT actually contains:

ActionRows
Deletett_25, tt_res
Addmc_25, mc_res, stat, stat_res, and castalia_mc_models.scs section mos_mis_params_25
Keep untouchedall 44 remaining tt_* rows, including tt (1.0 V core MOS) and tt_mim, and the three stat_mis_* rows

→ 52 rows. Verified: batch Spectre 20.1, zero errors, process spread active (rnpolywo 947.8 / 973.3 / 984.2 Ω across three draws).

Do not swap tt → mc. anatop_controlamp and anatop_biasgen_local contain only nch_25_mac / pch_25_mac and rnpolywo, so the 1.0 V core MOS family is irrelevant here — and tt and mc collide the same way tt_25 and mc_25 do, needing a second shim for the core mismatch parameters. Leave it typical.

tt_mim likewise stays: it declares par_mim for stat_mis_mim to vary, and A1 has no MIM cap (C_L is an ideal analogLib capacitor). Swap it to mc_mim + stat_mim only when you run this recipe on the SAR CDAC.

2.2.2 Or skip the table entirely: castalia_mc_models.scs

Everything in §2.1, §2.2 and §2.2.1 is packaged as castalia/ic/models/castalia_mc_models.scs. Spectre sections may contain include statements — the PDK does this itself — so the whole row set collapses into one row, and the section name selects the variation type:

Model FileSectionContentsUse with
/home/mseminario2/chips/castalia/ic/models/castalia_mc_models.scs castalia_typ_2546 tt_* — exactly today's list, no statistics single runs, DC sweeps, corner sweeps
castalia_mm_25+ stat_mis_25 / _res / _mim = 49 MC, variation = Mismatch
castalia_pm_2544 tt_* (no tt_25/tt_res) + stat + stat_res + 3 × stat_mis_* + mc_25 + mc_res + the parameter shim inline = 52 MC, variation = Process & Mismatch
mos_mis_params_25the bare shim, §2.2 row 1 hand-built row tables only

Select exactly one — each carries a complete device-family set and any two of them together are the SFE-59 duplicate-parameter failure.

Why this is the route to prefer. The row set is the thing that goes wrong on this chip, and it goes wrong silently. One row cannot drift between tests, cannot be half-edited, and reads the same in a test's Model Libraries list as it does in a corner's Model Files table. The stat-family omission that this document previously got wrong is exactly the kind of mistake a 52-row table invites.
Selecting castalia_typ_25 under a montecarlo statement fails loudly, which is deliberate: 
ERROR (SPECTRE-16011): mc1: Attempt to run Monte Carlo analysis with mismatch
variations, but no mismatch variations were specified in the statistics block.
So the typical section cannot silently produce a σ you might publish. This is the one silent-zero door the file closes outright.
ic/ is not under git (see CLAUDE.md), so this file is unversioned like the rest of the castalia library. Back it up or relocate it into the vestarv repo and point the model rows at the absolute path there.

2.6 One run can mix mismatch-only and process tests

The variation type is a per-run MC option, not per-test — which suggests you need two runs, one per variation type. You do not. Verified in batch Spectre 20.1, same seed, same numruns, on the two-device probe netlist:

Test's model sectionRun's variation settingWhat actually variedDiagnostic
castalia_mm_25mismatch mismatch onlyclean
castalia_mm_25all mismatch only — results bit-identical to the row above SPECTRE-16010 warning
castalia_pm_25all process + mismatchclean
castalia_pm_25mismatch mismatch only — process silently dropped nothing. No error, no warning, not even SPECTRE-16010.
castalia_mm_25process nothing — the test diesERROR (SPECTRE-16008)
castalia_pm_25process process only — mismatch off; two identical devices return identical currents within each drawclean, which is the problem

The setting is a request, not a selection. What actually varies is the intersection of the request and the statistics blocks the model rows supply — which is why one setting behaves differently on two tests in the same run. process is never right for this chip: it discards the matching data that every offset and INL spec depends on.

Rule: set the run to Process & Mismatch and let each test's model section decide. A castalia_mm_25 test in such a run returns exactly what a dedicated mismatch run would, so results stay comparable across runs, and one 200-point run can characterise the whole block.
The last row is the worst failure mode in this document. Setting the run to Mismatch when any test carries castalia_pm_25 degrades that test to mismatch-only and emits no diagnostic whatsoever — not even the SPECTRE-16010 that flags the reverse case. You would publish a drive-compliance σ that is several times too tight with nothing in any log to contradict it. Check the run-mode option, not the model rows, when a process σ comes back suspiciously small.

2.7 Nothing to do on the instances

All 60 devices in anatop_controlamp already carry mismatchflag=1 and sigma=1 from the PDK CDF defaults — verified in the generated netlist. No schematic edit is required to enable mismatch.

3 · Building the MC test

For a1_mc, host it on the existing DriveWBiasTB schematic view — it is already the unity-gain buffer with an I_load current source on the output and V_CM fixed at 1.25 V.

  1. Create a test on castalia / anatop_tb_controlamp / DriveWBiasTB, simulator spectre. Name it MismatchTB.
  2. Setup → Simulation Files → Include Path = /opt/design_kits/TSMC65-PDK/models/spectre. New tests come up with this blank; without it the corner model files fail to resolve with SFE-868.
  3. Setup → Model Libraries — the six rows from §2.1.
  4. Design variables: VDD25 2.5, V_CM 1.25, C_L 10p, b6_BiasAdj 37, and iload = 0.
  5. Analyses: dc only, no sweep, with Save DC Operating Point ticked. Disable every other analysis.
  6. Output: 
    voff = VDC("/V_OutOL") - VAR("V_CM")
itot = abs(IDC("/POWER/SRC_VDD25/PLUS"))     ; optional, supply spread
  7. Temperature: the plan's C0 is 37 °C (on-body operating point). The imported tsmcN65_typ_* corners all sit at 25 °C, so set this explicitly or the σ you publish is not at the operating condition the spec is written against.

4 · Creating the run plan

Monte Carlo is a run mode in Assembler, so switching the active setup to MC would apply it to every enabled test. A run plan keeps the active setup intact.

4.1 Open the assistant

Create → Run Plan, or Window → Assistants → Run Plan. It docks to the right of the Outputs pane and starts empty.

4.2 Create the run

Click Create New Run using Active Setup on the assistant toolbar. You get Run.1; expand its tree.

Use using Active Setup, not the blank Create New Run. It copies the tests, global variables, parameters and corners into the run so everything you need to switch off is visible in the tree. A blank run that contains no corners of its own falls back to the active setup's enabled corners — all five — without saying so.

4.3 Change the run mode

Right-click the run-mode line inside Run.1 (it reads Single Run, Sweeps and Corners) → Choose Run Mode → Monte Carlo Sampling.

4.4 Monte Carlo options

Right-click that same Monte Carlo Sampling line → Simulation options.

Number of Points200
Sampling MethodLow-Discrepancy Sequence if offered, else Latin Hypercube. Both converge faster than Random for a given N.
Monte Carlo SeedFix it and record it — you will want to reproduce this run when the TRM section is written.
Statistical variationProcess & Mismatch, always — even for a run that contains mismatch-only tests. See §2.7: the per-test model section decides what actually varies, so one run can mix both kinds of test. Setting this to Mismatch instead silently strips process variation from every castalia_pm_25 test. Label wording varies by release; §6 confirms it regardless.
Save dataEnable per-point data, otherwise you get summary statistics with no histogram.
Starting Run Number1

4.5 Prune tests and corners

  • Under Tests, uncheck everything except MismatchTB. (Right-click → Delete also works; unchecking is reversible.)
  • Under Corners, leave only _default (or the purpose-built C0_mm37 / C0_pm37 of §2.5) enabled — select the rest, right-click → Disable. This is not just about runtime: the imported tsmcN65_typ_* corners replace the test's model list with one that has no stat_mis_* rows, so leaving one enabled silently disables mismatch (§2.4).

None of this touches the active setup. That is the point of using a run plan.

4.6 Execute

Right-click Run.1 → Run to execute just this run. The toolbar's Execute Plan button runs every run in the plan. A history checkpoint appears as Run.1.n and results show on the Results tab.

6 · Verifying the run actually varied what you think

Do this before trusting any number. Once the run starts, open the generated netlist:

ic/.simulation/castalia/anatop_tb_controlamp/maestro/results/maestro/<History>/1/<Test>/netlist/input.scs

Mismatch-only run:

grep -n  "montecarlo"        input.scs   # must exist: variations=mismatch numruns=200
grep -c  "section=stat_mis"  input.scs   # must be 3
grep -c  "section=tt_25"     input.scs   # must be 1  (declares parn*_25)
grep -c  "mismatchflag=1"    input.scs   # must be 60 in anatop_controlamp
grep -oE "temp=[0-9.]+"      input.scs   # must be 37

Process + mismatch run:

grep -n  "montecarlo"                    input.scs   # variations=all numruns=200
grep -cE "section=(stat|stat_res|stat_mim)$"  input.scs   # must be 3
grep -c  "section=stat_mis"              input.scs   # must be 3
grep -cE "section=mc_(25|res|mim)$"      input.scs   # must be 3
grep -c  "section=tt_"                   input.scs   # must be 0 for these three families
grep -c  "parn1_25=0"                    input.scs   # must be 1 (the shim file, §2.2 row 1)

6.1 If you used the one-row file (§2.2.2), the greps change

The 46–52 include lines now live inside castalia_mc_models.scs, so they do not appear in input.scs. A grep -c "section=stat_mis" returns 0 on a perfectly good run. Check these instead:

grep -n "castalia_mc_models.scs" input.scs   # exactly 1 row; the section= tells you the variant
grep -n "montecarlo"             input.scs   # variations, numruns, seed
grep -oE "temp=[0-9.]+"          input.scs   # 37

That is the point of the file: the row set is fixed content under version control rather than GUI state, so it cannot drift and does not need re-verifying per run. What still needs verifying is which section got selected — one grep instead of five counts.

6.2 Spectre tells you which statistics families are missing — read it

Three codes, all worth recognising on sight. The first two are fatal, the third is the mismatch-only run confirming itself:

CodeSeverityTextMeans
SPECTRE-16011ERROR "…with mismatch variations, but no mismatch variations were specified in the statistics block" variations=mismatch with no stat_mis_*. Selecting castalia_typ_25 for an MC run does this.
SPECTRE-16012ERROR "…with process and mismatch variations, but no variations were specified in the statistics block" variations=all with no statistics sections at all. This is what killed Plan.0.Run.0 — 50 of 50 point-groups, 200 samples, zero data (§8.1).
SPECTRE-16010Warning "…but no process variations were specified in the statistics block" Mismatch statistics present, process statistics absent. Expected and correct on a castalia_mm_25 run. It must disappear when you switch to castalia_pm_25 — if it is still there, the stat rows did not take.
SPECTRE-16010 vanishing is the cheapest possible confirmation that a process MC is genuinely varying process. Check it before the σ numbers, not after.
Second-order check, worth 30 seconds. On a process run, σ of any bias current must be non-zero: add i_tail = OP("/OPAMP/M10" "id") as an output and look at the Detail view. If it is constant across samples, the stat rows did not take even though the run completed — the same class of silent failure as σ(voff) = 0, one family up.

8 · Reference numbers for a1_mc

Measured through this exact recipe in batch Spectre, 30 mismatch samples, tt models at 27 °C, b6_BiasAdj = 37, buffer at VCM = 1.25 V:

σ(voff)2.56 mV (±0.34 mV, 1σ CI at n = 30)
mean(voff)+0.44 mV
range−6.59 … +4.32 mV
This is over the plan's σ ≤ 2 mV budget. At 30 samples the confidence interval is roughly [2.2, 2.9] mV, so it is likely a genuine fail rather than sampling noise — but the full 200-point run is what settles it. If confirmed, the options are a larger input pair, a trim, or a renegotiated budget; voff lands directly on the commanded cell potential as a systematic error on every measurement the channel makes, and unlike the drive-compliance shortfall it cannot be fixed by adding an output stage.

The Run Plan assistant's Save Script to Run Plan in Batch button writes a runPlan.il:

History checkpoints are saved into the maestro cellview exactly as for an interactive run. Do this once the run is known good — a 200-point MC is precisely the thing to re-run unattended after any change to A1, and the script is the reproducible artifact to cite when the TRM quotes σ.

11 · Which specs to put in the MC, and the outputs that read them

Offset alone is not a characterisation. The tests below already exist as views on castalia / anatop_tb_controlamp — UnityFeedbackWBiasTB (buffer + IPRB1 + stb), DriveWBiasTB, StepUnityFeedbackWBiasTB, OffsetCalTB — so this is mostly a matter of enabling them inside the MC run and adding outputs, not building benches. All four have operating points valid for every sample, which is the §1.1 requirement.

isink_max is the single most important statistical number on this block. Nominal is 3.5 µA of sink against the ±33 µA rev-2 target. Its σ and its worst-of-200 decide whether the fix is mandatory and how large it must be — and it is a process-dominated quantity, so it only means anything in the §2.2 run.

11.3 Adding the outputs — exact GUI steps

  1. Outputs Setup pane (Data View → Outputs tab), click the first empty row, set Type = expr.
  2. Name = e.g. isink_max; Details = the expression string above.
  3. Test column — pick the owning test. An expression attached to the wrong test returns nothing, silently.
  4. Tick Save; tick Plot for anything you want a histogram of.
  5. Spec column — enter the limit (< 2m for voff, > 60 for pm, > 33u for isink_max). This is what makes Assembler compute yield. Without a Spec you get numbers and no yield column.

Then in the Run Plan tree, under Tests, tick OffsetCalTB, UnityFeedbackWBiasTB, DriveWBiasTB, StepUnityFeedbackWBiasTB and untick the rest. Especially untick DriveMapTB — its 26 × 1601 grid × 200 samples will run for days.

One sample set is generated per run, so with a fixed seed every enabled test sees the same draws. Sample n's voff and isink_max are therefore paired, and plotting one against the other finds the common root cause. Keep the same seed across the mismatch-only and process runs too, and across any re-run after a design change — paired samples make a small σ improvement visible that unpaired runs would bury in sampling noise.

Two statistics traps specific to this chip.
  1. Check normality before quoting σ. voff is Gaussian. isink_max, pm and the sat_* margins are clipped or skewed — quote 1st/99th percentiles and worst-of-N for those, not mean ± 3σ.
  2. Four channels change the yield arithmetic. The channels share only the biasgen and the vcm DAC, so chip yield ≈ p4 and 95 % chip yield needs 98.7 % per channel — about 2.5σ, not 3σ. For any channel-to-channel comparison the relevant spread is σΔ = √2·σ, since the shared blocks contribute common-mode error and cancel.
