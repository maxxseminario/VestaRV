\section{System Configuration} \label{s:config}
The microcontroller (MCU) described in this document is a \NumHartsWord-hart (\NumHartsWord-core) multiprocessor built from \NumHartsWord{} identical VestaRV CPU cores, a custom 32-bit RISC-V processor. The microcontroller is composed of the \NumHartsWord{} VestaRV harts, a ROM that contains boot software and a Forth interpreter, private RAM memory cells per hart, an arbitrated shared memory window for inter-hart communication, and several peripherals. The multi-core architecture is described in Section~\ref{s:multicore}. The modular architecture enables customization of the peripheral set, memory configuration, and system features to match specific application requirements. Figure~\ref{fig:chip-system-diagram} shows the top-level organization of this configuration.

\subsection{Chip Configuration} \label{ss:chipConfig}

This document, the memory-map headers, the linker scripts, and the drop-in RTL are all generated from one chip configuration by \texttt{make chip}. The configuration is a small JSON document (every key optional; missing keys keep the \AsicNameForUserGuide{} defaults) passed as \texttt{make chip CONFIG=config.json}; an interactive front-end for producing it ships with the generator (\texttt{docs/chip\_configurator.html}). Table~\ref{t:chip-config} lists every configuration knob together with the value used to build \emph{this} document, and Table~\ref{t:chip-config-derived} lists the geometry derived from those knobs. The resolved configuration is also written to \texttt{config/ChipConfig.resolved.json} at every build, and \texttt{make verify [CONFIG=config.json]} \emph{proves} a configuration: it stages the generated RTL into a behavioral simulation environment and runs the multi-core boot/ISA smoke suite against it. The core peripheral set and the pad ring are not configuration knobs; they are fixed template content, and the pad ring (Section~\ref{s:pinsConfig}) is derived from the generator's package model. The second-instance peripherals (\peripheral{UART1}, \peripheral{SPI1}, \peripheral{TIMER1}, \peripheral{I2C1}) and the \peripheral{NPU}, however, are individually droppable through the \texttt{peripherals} section: a dropped instance's register window reads zero, its interrupt vectors are reserved (the numbering is frozen), and its pins revert to plain GPIO.

The 32-bit memory bus on the MCU is in the von Neumann architecture. All addressable memory elements (i.e. the ROM, RAM, and memory mapped registers) are all located on a single bus. A pointer can access any of these locations in memory.

The ROM cell contains boot code, which is read-only. Each SRAM cell can be read or written to, and may contain both program and variable information. The chip carries no on-die non-volatile memory: it boots from an \emph{external} SPI flash device, and hart 0, and only hart 0, can additionally read that flash directly, and execute in place from it, through the extended-flash window at \texttt{\FlashBaseAddress} and above (the last region in Figure~\ref{fig:address-space}; see Section \ref{ss:spi-flash-xip}). At reset every hart fetches from the boot ROM at \texttt{\RomStartAddress} and dispatches on its hart ID: hart 0 copies the application image out of the flash into memory and enters it, and the remaining harts park until hart 0 loads and launches them (Section \ref{ss:multicore-boot}). Each SRAM and ROM cell can be individually powered off or on using the \peripheral{SYSTEM} peripheral. When powered off, the cells use less power and cannot be read or written to. SRAM cells that are powered off do not retain their previous data, and the data becomes undefined.


The interrupt vector table (IVT) begins at address \texttt{\VectorsStartAddress} and contains jump instructions to the interrupt service routines (ISRs). When an interrupt occurs, the CPU directly vectors to the corresponding entry in the IVT, which then jumps to the appropriate ISR. Each IVT entry is 4 bytes and typically contains a RISC-V jump instruction (e.g., \asminline{j handler}). The IVT can be initialized and configured in software, allowing flexible interrupt routing and handler assignment at runtime.

Figure~\ref{fig:address-space} is a single address column drawn for all \NumHartsWord{} harts, and its braces name who reaches each region. Everything below \texttt{\FlashBaseAddress} other than the private band is the \emph{shared window}: every hart reaches it through the arbiter, and all \NumHartsWord{} harts see the same memory there (Section~\ref{s:multicore}). The private band is the exception: at those addresses a hart reaches its own tightly-coupled memory (TCM) instead of the shared bus, so the same address names a different \TcmSizeKiB{} KiB of RAM in each hart, and no hart can reach another's directly.
\iforchpresent
The TCM apertures are the one sanctioned way across that line: hart 0, the orchestrator, reads hart $h$'s private TCM through the aperture at \texttt{\FirstTcmWindowAddress}${} + h \times{}$\TcmSizeKiB{} KiB. The apertures are read-only, and any other hart reading them gets zeros (Section~\ref{s:multicore}).

% Startup and reset behavior
\section{Startup and Reset Behavior} \label{s:startup}
To place the MCU in reset mode, drive the \pin{resetn} pin LOW (asserted). To take the MCU out of reset mode, let the \pin{resetn} pin go high (deasserted). The \pin{resetn} pin has an internal 47~\si{\kilo\ohm} pullup resistor which constantly attempts to pull the \pin{resetn} pin HIGH. If the user does not wish to use the \pin{resetn} pin, it is safe to leave it unconnected.

When the MCU is first powered up, a power-on reset (POR) circuit resets the MCU. As the core voltage, beginning at 0~V, begins to climb, the POR circuit does not assert the internal reset. Once the core voltage reaches a particular value (which is temperature and process dependent, but typically around 0.7~V), the POR circuit asserts the internal reset signal for about 20 ns and then deasserts it. If either the \pin{resetn} pin or the POR reset signal is asserted, the MCU will be in reset mode. In reset, the memory mapped registers and CPU state variables are all reset to their powerup values.

When the MCU comes out of reset, it immediately begins to execute the bootloader stored in the ROM, setting the program counter to address \texttt{0x0000}. If the \pin{BOOT} pin is LOW, the bootloader launches a Forth interpreter which communicates over \peripheral{UART0} at 115,200 baud (see Section \ref{s:forth} for details concerning the Forth interpreter). If the \pin{BOOT} pin is HIGH, the bootloader reads and executes the program stored on an external SPI flash on \peripheral{SPI0} (see Section \ref{s:programming} for details on how to program the MCU). When the bootloader reads the program stored in the SPI flash, it dumps the contents of the SPI flash directly into RAM, completely filling the RAM from beginning to end using an address-to-address copy. After the bootloader has copied the program stored in the SPI flash into RAM, it jumps (moves the program counter) to address \texttt{\SpiFlashProgramAddress} and begins executing the code.

Only hart 0 executes the boot ROM and the SPI-flash boot sequence described above. Harts 1--\MaxHartIndex{} come out of reset executing from their private RAM and park until hart 0 releases them through the boot mailboxes in shared RAM; see Section \ref{ss:multicore-boot}.

Note that the boot ROM reprograms the clock system during boot, so the SMCLK source at application entry is a boot-ROM implementation detail; in particular, it may be left on the slow LFXT (32.768~\si{\kilo\hertz}) source. Applications that use SMCLK-domain peripherals (the UARTs, SPIs, I\textsuperscript{2}Cs, or a timer clock-source switch) should therefore always select their desired SMCLK source in the \peripheral{SYSTEM} peripheral first, rather than relying on the boot-time clock state; see Section \ref{ss:clocks} and the clock handoff note in the \peripheral{TIMERx} chapter.

The VestaRV CPU implements an interrupt system with \VectorsCount{} interrupt vectors, numbered 0--\TopVector, whose sources are enumerated in the table above. The numbering is frozen: a vector belongs to the block that owns it whether or not this configuration instantiates that block, so vectors whose block is absent are reserved and counted with the rest rather than shifting the ones above them. Two of the \VectorsCount{} are the \peripheral{CLINT} pair (\ClintMsipVector, software/inter-processor interrupt; \ClintMtipVector, timer interrupt) added for multi-core operation; the other \RoutedVectorsCount{} sit on the \peripheral{IRQROUTER} side of the fabric --- the peripheral and system sources, the reserved slots frozen among them, and \texttt{meip}'s own slot. Each hart takes three interrupt lines: its own \peripheral{CLINT} software and timer interrupts (vectors \ClintMsipVector{} and \ClintMtipVector, hardwired enabled, delivered on dedicated per-hart wires) and the external interrupt \texttt{meip} (vector \MeipVector, a slot of its own that no source pends on), which delivers \textit{all} peripheral and system sources through the \peripheral{IRQROUTER}'s claim/complete mechanism: the vector-\MeipVector{} handler reads the router's \register{CLAIM} register to discover and claim the pending source, dispatches on the returned vector number, and writes it back to complete (see the \peripheral{IRQROUTER} chapter). Which sources reach which hart is programmed per hart in the router's routing rows, identical for every hart, hart 0 included. All peripheral sources are masked by default upon MCU reset and must be explicitly routed in software before use; source priority is fixed (the lowest pending vector number is claimed first). Additionally, peripherals generating interrupts must be configured to enable interrupt generation at the peripheral level.

\subsection{Interrupt Vector Table}

The interrupt vector table (IVT) is located at the base of RAM, beginning at address \texttt{\VectorsStartAddress}. Unlike traditional pointer-based interrupt vector tables, the VestaRV IVT contains direct jump instructions to the interrupt service routines (ISRs). Each entry in the IVT is a 4-byte RISC-V jump instruction (e.g., \asminline{j handler}) that vectors execution immediately to the corresponding ISR when an interrupt occurs. This architecture eliminates the indirection overhead of loading function pointers and provides deterministic, low-latency interrupt response.

While the VestaRV hardware does not mandate a specific IVT structure, it is strongly recommended to populate the IVT with jump instructions during system initialization. The automatic code generation tools produce linker scripts and initialization code that configure the IVT at the beginning of RAM. The memory map header files provide macros to facilitate proper ISR placement and IVT entry configuration.

\subsection{Interrupt Entry, Exit, and Recursion}

When an interrupt is taken, the hardware saves a minimal context: it pushes the return program counter (one 32-bit word) onto the system stack at $\mathtt{sp}-4$, decrements \asminline{sp} by 4, and vectors execution through the IVT entry for the interrupt. \textbf{No other state is saved by hardware.} Software is responsible for saving and restoring every general-purpose register the interrupt service routine (ISR) uses. The generated runtime provides an interrupt entry wrapper (in the startup code) that saves the general-purpose registers on the stack (about 120 bytes per interrupt level), calls the C-level handler, restores the registers, and returns with the \asminline{retirq} instruction, so C-coded ISRs need no special handling. Hand-written assembly ISRs must perform the equivalent save/restore themselves. Executing \asminline{retirq} pops the hardware-saved program counter, increments \asminline{sp} by 4, and resumes execution at the interrupted location.

Because the very first thing interrupt entry does is a store at $\mathtt{sp}-4$, \textbf{the stack pointer must point at valid, writable private memory before interrupts are enabled}. This applies to every hart: a freshly released tile hart must load its stack pointer before unmasking interrupts or going to sleep (see Section \ref{s:multicore}).

Interrupt handling is non-recursive: a running ISR is never preempted, and further pending interrupts (including a pending \peripheral{CLINT} interrupt during a vector-85 service) are taken after the current ISR returns. Stack allocation must cover one interrupt level: the 4-byte hardware-saved return address plus the handler's register frame (about 120 bytes for the runtime wrapper) and the ISR's local variables. (The single-core chip's priority-tier and recursion machinery was retired together with the \peripheral{SYSTEM} interrupt registers; source arbitration now happens in the \peripheral{IRQROUTER}.)

\subsection{Sleep Mode and Interrupt Wake-Up}

If an interrupt occurs while the CPU is in sleep mode, the processor will automatically wake from sleep and service the interrupt. Upon execution of the \asminline{retirq} instruction, the CPU will return to sleep mode unless the ISR or woken code explicitly reconfigures the clock and power settings. During sleep mode, the CPU clock is gated to conserve power, but all register contents and the program counter are retained. If the clock source for MCLK is disabled during sleep, any enabled interrupt will automatically power up and enable the source clock for the duration of interrupt servicing.

Clock and power management, including sleep mode configuration, are controlled through the \peripheral{SYSTEM} peripheral. Note that if SMCLK is disabled, peripherals may be unable to assert interrupt signals, potentially preventing wake from sleep.

\section{CPU Instructions and Assembly} \label{s:cpu-instructions}

The \AsicNameForUserGuide{} MCU integrates the VestaRV CPU core, a custom 32-bit RISC-V processor implementing the RV32IMAC instruction set with bit manipulation extensions (Zba, Zbb, Zbc, Zbs). This configuration provides integer arithmetic (I), hardware multiplication and division (M), atomic operations (A), compressed 16-bit instructions (C), and enhanced bit manipulation capabilities. The RISC-V instruction set architecture (ISA) defines the binary encoding of machine instructions, their operational semantics, and the register architecture used for computation and control flow.

\subsection{CPU Registers}

There are 32 CPU registers defined in the RISC-V ISA. Though the user can technically use any register for any purpose (except for \asminline{x0}/\asminline{zero}, which is read-only and is always equal to 0x00000000), it is generally advisable to use each register for its intended purpose and follow the convention that the RISC-V ISA describes. The convention was created to create a standard use for each register so that assembly functions can be written that will be compatible with any RISC-V assembly program. The RISC-V compiler always follows this convention. Therefore, if the user also follows the convention, then the user's assembly code will be drop-in compatible with other compiled code (such as C code). If the user does not follow the convention, then it may cause many runtime errors.

Each register has a specific purpose and a designated ``saver'' that is allowed to write to it. The saver is either the caller (the code that calls a function) or the callee (the function that was called). This allows for communication between caller and callee such that arguments can be passed from caller to callee and returned data can be sent back from callee to caller. For example, the registers \asminline{a0-a7} are intended for function arguments and are written to by the caller. Registers \asminline{s0-s11} are preserved across function calls and are written to by the callee. Furthermore, registers \asminline{t0-t6} are temporary register that can be used for any purpose and are written to by the caller.

In assembly, registers can be referred to interchangibly by their register number or name (e.g. you can either type \asminline{x1} or \asminline{ra} to refer to the same register). Generally, one should only use the register names since they give hints as to the purpose of the register.

A CPU instruction can have up to two source register \asminline{rs1} and \asminline{rs2}, and up to one destination register \asminline{rd}. \asminline{rs1}, \asminline{rs2}, and \asminline{rd} can be any of the 32 CPU registers (e.g. \asminline{sp}, \asminline{t6}, \asminline{zero}, etc.). The source registers are used as ``arguments'' to the instruction and are not modified by the instruction, and the destination register is modified by the instruction as its output.

\subsection{Load/Store Memory Instructions}

These instructions interface between the memory bus (containing RAM, ROM, and memory-mapped registers) and the CPU registers. They are used to load data from memory into a CPU register or store data from a CPU register into memory. The immediate parameter (\asminline{i}) refers to a hard-coded 12-bit constant that is stored inside the CPU instruction itself and is added to the value of one of the registers. All load/store instructions take 2 MCLK cycles to execute.

\begin{itemize}
	\item Load Signed Byte: \asminlinehl{lb rd, I(rs1)}: loads the signed byte (8 bits) stored at memory location pointed to by (\asminline{rs1} + \asminline{I}) into the destination CPU register \asminline{rd}
	\item Load Unsigned Byte: \asminlinehl{lbu rd, I(rs1)}: loads the unsigned byte (8 bits) stored at memory location pointed to by (\asminline{rs1} + \asminline{I}) into the destination CPU register \asminline{rd}
	\item Load Signed Half Word: \asminlinehl{lh rd, I(rs1)}: loads the signed half word (16 bits) stored at memory location pointed to by (\asminline{rs1} + \asminline{I}) into the destination CPU register \asminline{rd}
	\item Load Unsigned Half Word: \asminlinehl{lhu rd, I(rs1)}: loads the unsigned half word (16 bits) stored at memory location pointed to by (\asminline{rs1} + \asminline{I}) into the destination CPU register \asminline{rd}
	\item Load Word: \asminlinehl{lw rd, I(rs1)}: loads the signed or unsigned word (32 bits) stored at memory location pointed to by (\asminline{rs1} + \asminline{I}) into the destination CPU register \asminline{rd}
	\item Store byte: \asminlinehl{sb rs1, I(rs2)}: stores the signed or unsigned byte (8 bits) from source CPU regsiter 1 \asminline{rs1} into the memory location pointed to by (\asminline{rs2} + \asminline{I})
	\item Store half word: \asminlinehl{sh rs1, I(rs2)}: stores the signed or unsigned half word (16 bits) from source CPU regsiter 1 \asminline{rs1} into the memory location pointed to by (\asminline{rs2} + \asminline{I})
	\item Store word: \asminlinehl{sh rs1, I(rs2)}: stores the signed or unsigned word (32 bits) from source CPU regsiter 1 \asminline{rs1} into the memory location pointed to by (\asminline{rs2} + \asminline{I})
\end{itemize}

\subsection{Shift Instructions}

These instructions perform bit shift operations (e.g. \cinline{<<}). The immediate parameter (\asminline{I}) refers to a hard-coded 12-bit constant that is stored inside the CPU instruction itself and is used as the number of bits to shift. Each shift instruction takes 1 MCLK cycle to execute.

\begin{itemize}
	\item Shift Left: \asminlinehl{sll rd, rs1, rs2}: Logical shifts the value in \asminline{rs1} left by \asminline{rs2} bits and stores the result in \asminline{rd}.
	\item Shift Left Immediate: \asminlinehl{slli rd, rs1, I}: Logical shifts the value in \asminline{rs1} left by \asminline{I} bits and stores the result in \asminline{rd}.
	\item Shift Right: \asminlinehl{sll rd, rs1, rs2}: Logical shifts the value in \asminline{rs1} right by \asminline{rs2} bits and stores the result in \asminline{rd}.
	\item Shift Right Immediate: \asminlinehl{slli rd, rs1, I}: Logical shifts the value in \asminline{rs1} right by \asminline{I} bits and stores the result in \asminline{rd}.
	\item Shift Right Arithmetic: \asminlinehl{sll rd, rs1, rs2}: Arithmetic shifts the value in \asminline{rs1} right by \asminline{rs2} bits and stores the result in \asminline{rd}.
	\item Shift Right Arithmetic Immediate: \asminlinehl{slli rd, rs1, I}: Arithmetic shifts the value in \asminline{rs1} right by \asminline{I} bits and stores the result in \asminline{rd}.
\end{itemize}

\subsection{Arithmetic Instructions}

These instructions perform arithmetic operations. The immediate parameter (\asminline{I}) refers to a hard-coded 12-bit signed integer that is stored inside the CPU instruction itself and is added to the operation (except for in the \asminline{auipc} instruction). These instructions take 1 MCLK cycle to execute.

\begin{itemize}
	\item Addition: \asminlinehl{add rd, rs1, rs2}: Adds the signed/unsigned integer values in \asminline{rs1} and \asminline{rs2} together and stores the sum in \asminline{rd}
	\item Addition Immediate: \asminlinehl{addi rd, rs1, I}: Adds the signed/unsigned integer value in \asminline{rs1} with the immediate 12-bit signed integer \asminline{I} together and stores the sum in \asminline{rd}
	\item Subtraction: \asminlinehl{sub rd, rs1, rs2}: Subtracts the signed/unsigned integer values in \asminline{rs1} from \asminline{rs2} and stores the result in \asminline{rd} (i.e. \asminline{rd} $\leftarrow$ \asminline{rs1} $-$ \asminline{rs2})
	\item Load Upper Immediate: \asminlinehl{lui rd, I}: Loads the 20-bit immediate value \asminline{I} into the upper 20 bits of the destination CPU register \asminline{rd} (the lower 12 bits are all cleared to 0s)
	\item Add Upper Immediate to PC: \asminlinehl{auipc rd, I}: Adds the 12-bit signed integer immediate \asminline{I} to the program counter to jump the program's execution to a location \asminline{I} away from the current program counter. Note that \asminline{I} can be negative.
\end{itemize}

\subsection{Bitwise Instructions}

These instructions perform bitwise operations. The immediate parameter (\asminline{I}) refers to a hard-coded 12-bit signed integer that is stored inside the CPU instruction itself and is used as one of the operands of the bitwise operations. These instructions take 1 MCLK cycle to execute.

\begin{itemize}
	\item Bitwise exclusive OR: \asminlinehl{xor rd, rs1, rs2}: Performs the bitwise XOR of \asminline{rs1} and \asminline{rs2} and stores the result in \asminline{rd}. 
	\item Bitwise exclusive OR Immediate: \asminlinehl{xori rd, rs1, I}: Performs the bitwise XOR of \asminline{rs1} and the immediate \asminline{I} and stores the result in \asminline{rd}.
	\item Bitwise OR: \asminlinehl{or rd, rs1, rs2}: Performs the bitwise OR of \asminline{rs1} and \asminline{rs2} and stores the result in \asminline{rd}. 
	\item Bitwise OR Immediate: \asminlinehl{ori rd, rs1, I}: Performs the bitwise OR of \asminline{rs1} and the immediate \asminline{I} and stores the result in \asminline{rd}.
	\item Bitwise AND: \asminlinehl{and rd, rs1, rs2}: Performs the bitwise AND of \asminline{rs1} and \asminline{rs2} and stores the result in \asminline{rd}. 
	\item Bitwise AND Immediate: \asminlinehl{andi rd, rs1, I}: Performs the bitwise AND of \asminline{rs1} and the immediate \asminline{I} and stores the result in \asminline{rd}.
\end{itemize}

\subsection{Comparison Instructions}

These instructions perform comparison operations. The results of these instructions are either true (0x00000001) or false (0x00000000). The immediate parameter (\asminline{I}) refers to a hard-coded 12-bit signed or unsigned integer that is stored inside the CPU instruction itself and is used as one of the operands of the bitwise operations. These instructions take 1 MCLK cycle to execute.

\begin{itemize}
	\item Set when Less Than: \asminlinehl{slt rd, rs1, rs2}: If \asminline{rs1 < rs2} (using signed integers), the destination register \asminline{rd} is set to 0x00000001, otherwise it is set to 0x00000000.
	\item Set when Less Than Immediate: \asminlinehl{slti rd, rs1, I}: If \asminline{rs1 < I} (using signed integers), the destination register \asminline{rd} is set to 0x00000001, otherwise it is set to 0x00000000.
	\item Set when Less Than Unsigned: \asminlinehl{sltu rd, rs1, rs2}: If \asminline{rs1 < rs2} (using unsigned integers), the destination register \asminline{rd} is set to 0x00000001, otherwise it is set to 0x00000000.
	\item Set when Less Than Immediate Unsigned: \asminlinehl{sltiu rd, rs1, I}: If \asminline{rs1 < I} (using unsigned integers), the destination register \asminline{rd} is set to 0x00000001, otherwise it is set to 0x00000000.
\end{itemize}

\subsection{Branch Instructions}

These instructions are conditional instructions that branch (jump) the program execution to a new location if the condition is met, or proceed on to the next instruction like normal if the condition is not met. The immediate parameter (\asminline{I}) refers to a hard-coded 12-bit signed integer that is stored inside the CPU instruction itself and is added to the program counter if the condition is met. Usually, in assembly, the program writer can simply provide the \textit{label} to the desired branch location/function in the program (e.g. \asminline{labelToFunction:}) rather than its actual memory location, which is usually not known before being built. These instructions take 1 MCLK cycle to execute regardless of whether the branch is taken or not.

\begin{itemize}
	\item Branch if Equal: \asminlinehl{beq rs1, rs2, I}: Branches to PC + \asminline{I} if \asminline{rs1} $=$ \asminline{rs2}, proceeds to the next instruction like normal otherwise.
	\item Branch if Not Equal: \asminlinehl{bne rs1, rs2, I}: Branches to PC + \asminline{I} if \asminline{rs1} $\neq$ \asminline{rs2}, proceeds to the next instruction like normal otherwise.
	\item Branch if Less Than: \asminlinehl{blt rs1, rs2, I}: Branches to PC + \asminline{I} if \asminline{rs1} $<$ \asminline{rs2} (signed integers), proceeds to the next instruction like normal otherwise.
	\item Branch if Greater Than or Equal: \asminlinehl{bge rs1, rs2, I}: Branches to PC + \asminline{I} if \asminline{rs1} $\geq$ \asminline{rs2} (signed integers), proceeds to the next instruction like normal otherwise.
	\item Branch if Less Than Unsigned: \asminlinehl{bltu rs1, rs2, I}: Branches to PC + \asminline{I} if \asminline{rs1} $<$ \asminline{rs2} (unsigned integers), proceeds to the next instruction like normal otherwise.
	\item Branch if Greater Than or Equal Unsigned: \asminlinehl{bgeu rs1, rs2, I}: Branches to PC + \asminline{I} if \asminline{rs1} $\geq$ \asminline{rs2} (unsigned integers), proceeds to the next instruction like normal otherwise.
\end{itemize}

\subsection{Jump and Link Instructions}

The jump and link instructions write the address of the next consecutive instruction in the program to the destination register, but then jump the program counter to another location in memory. These instructions are used to call new functions while preserving the ``return address'', or the memory location of the instruction to go back to after the function returns. The immediate parameter (\asminline{I}) refers to a hard-coded 20-bit signed integer that is stored inside the CPU instruction itself and is used to modify the program counter. Usually, in assembly, the program writer can simply provide the \textit{label} to the desired location/function in the program (e.g. \asminline{labelToFunction:}) rather than its actual memory location, which is usually not known before being built. All jump and link instructions take 1 MCLK cycle to execute.

\begin{itemize}
	\item Jump and Link: \asminlinehl{jal rd, I} Stores the return address to \asminline{rd} (which is usually the return address register \asminline{ra}) and then adds \asminline{I} to the program counter, effectively jumping to PC + \asminline{I}. 
	\item Jump and Link Register: \asminlinehl{jalr rd, rs1, I} Stores the return address to \asminline{rd} (which is usually the return address register \asminline{ra}) and then sets the program counter to \asminline{rs1} + \asminline{I}, effectively jumping to \asminline{rd1} + \asminline{I}.
\end{itemize}



\subsection{Atomic Memory Operations (A Extension)}

The VestaRV core implements the RISC-V Atomic (A) extension, providing atomic read-modify-write operations for multiprocessor synchronization. On the \AsicNameForUserGuide{} MCU these instructions are the standard way to build locks and shared counters in the arbitrated shared RAM: an \asminline{AMO} instruction holds the shared-window arbiter grant across its whole read-modify-write pair, and a failed \asminline{sc.w} has its write suppressed by the reservation unit, so both are atomic with respect to all \NumHartsWord{} harts (see Section \ref{ss:multicore-sync}). Do not use atomic instructions on hardware mutex addresses (see the \peripheral{MUTEX} peripheral chapter). All atomic memory operations operate on 32-bit words and take 5 MCLK cycles to execute.

\begin{itemize}
	\item Load Reserved: \asminlinehl{lr.w rd, (rs1)}: Loads a 32-bit word from memory address in \asminline{rs1} into \asminline{rd} and reserves the memory location for atomic access.
	\item Store Conditional: \asminlinehl{sc.w rd, rs2, (rs1)}: Conditionally stores the 32-bit word in \asminline{rs2} to the memory address in \asminline{rs1}. Returns 0 in \asminline{rd} on success, nonzero on failure.
	\item Atomic Swap: \asminlinehl{amoswap.w rd, rs2, (rs1)}: Atomically swaps the 32-bit word at memory address in \asminline{rs1} with the value in \asminline{rs2}, storing the original memory value in \asminline{rd}.
	\item Atomic Add: \asminlinehl{amoadd.w rd, rs2, (rs1)}: Atomically adds \asminline{rs2} to the 32-bit word at memory address in \asminline{rs1}, storing the original memory value in \asminline{rd}.
	\item Atomic XOR: \asminlinehl{amoxor.w rd, rs2, (rs1)}: Atomically performs bitwise XOR of \asminline{rs2} with the 32-bit word at memory address in \asminline{rs1}, storing the original memory value in \asminline{rd}.
	\item Atomic AND: \asminlinehl{amoand.w rd, rs2, (rs1)}: Atomically performs bitwise AND of \asminline{rs2} with the 32-bit word at memory address in \asminline{rs1}, storing the original memory value in \asminline{rd}.
	\item Atomic OR: \asminlinehl{amoor.w rd, rs2, (rs1)}: Atomically performs bitwise OR of \asminline{rs2} with the 32-bit word at memory address in \asminline{rs1}, storing the original memory value in \asminline{rd}.
	\item Atomic Minimum: \asminlinehl{amomin.w rd, rs2, (rs1)}: Atomically compares \asminline{rs2} with the 32-bit signed word at memory address in \asminline{rs1}, storing the minimum value to memory and the original memory value in \asminline{rd}.
	\item Atomic Maximum: \asminlinehl{amomax.w rd, rs2, (rs1)}: Atomically compares \asminline{rs2} with the 32-bit signed word at memory address in \asminline{rs1}, storing the maximum value to memory and the original memory value in \asminline{rd}.
	\item Atomic Minimum Unsigned: \asminlinehl{amominu.w rd, rs2, (rs1)}: Atomically compares \asminline{rs2} with the 32-bit unsigned word at memory address in \asminline{rs1}, storing the minimum value to memory and the original memory value in \asminline{rd}.
	\item Atomic Maximum Unsigned: \asminlinehl{amomaxu.w rd, rs2, (rs1)}: Atomically compares \asminline{rs2} with the 32-bit unsigned word at memory address in \asminline{rs1}, storing the maximum value to memory and the original memory value in \asminline{rd}.
\end{itemize}

\subsection{Bit Manipulation Instructions (Zb* Extensions)}

The VestaRV core implements several bit manipulation extensions (Zba, Zbb, Zbc, Zbs) that provide efficient operations for bit-level data manipulation, cryptographic primitives, and address generation. All bit manipulation instructions execute in 1 MCLK cycle.

\subsubsection{Address Generation (Zba)}

\begin{itemize}
	\item Shift Left Add: \asminlinehl{sh1add rd, rs1, rs2}: Shifts \asminline{rs1} left by 1 bit, adds \asminline{rs2}, and stores result in \asminline{rd}. Equivalent to \asminline{rd = (rs1 << 1) + rs2}.
	\item Shift Left Add 2: \asminlinehl{sh2add rd, rs1, rs2}: Shifts \asminline{rs1} left by 2 bits, adds \asminline{rs2}, and stores result in \asminline{rd}. Equivalent to \asminline{rd = (rs1 << 2) + rs2}.
	\item Shift Left Add 3: \asminlinehl{sh3add rd, rs1, rs2}: Shifts \asminline{rs1} left by 3 bits, adds \asminline{rs2}, and stores result in \asminline{rd}. Equivalent to \asminline{rd = (rs1 << 3) + rs2}.
\end{itemize}

\subsubsection{Basic Bit Manipulation (Zbb)}

\begin{itemize}
	\item AND with Inverted: \asminlinehl{andn rd, rs1, rs2}: Performs bitwise AND of \asminline{rs1} with the bitwise complement of \asminline{rs2}, storing result in \asminline{rd}.
	\item OR with Inverted: \asminlinehl{orn rd, rs1, rs2}: Performs bitwise OR of \asminline{rs1} with the bitwise complement of \asminline{rs2}, storing result in \asminline{rd}.
	\item XOR with Inverted: \asminlinehl{xnor rd, rs1, rs2}: Performs bitwise XOR of \asminline{rs1} with the bitwise complement of \asminline{rs2}, storing result in \asminline{rd}.
	\item Count Leading Zeros: \asminlinehl{clz rd, rs1}: Counts the number of consecutive zero bits starting from the most significant bit in \asminline{rs1}, storing the count in \asminline{rd}.
	\item Count Trailing Zeros: \asminlinehl{ctz rd, rs1}: Counts the number of consecutive zero bits starting from the least significant bit in \asminline{rs1}, storing the count in \asminline{rd}.
	\item Count Population: \asminlinehl{cpop rd, rs1}: Counts the number of set bits (1s) in \asminline{rs1}, storing the count in \asminline{rd}.
	\item Maximum: \asminlinehl{max rd, rs1, rs2}: Stores the maximum of \asminline{rs1} and \asminline{rs2} (signed comparison) in \asminline{rd}.
	\item Maximum Unsigned: \asminlinehl{maxu rd, rs1, rs2}: Stores the maximum of \asminline{rs1} and \asminline{rs2} (unsigned comparison) in \asminline{rd}.
	\item Minimum: \asminlinehl{min rd, rs1, rs2}: Stores the minimum of \asminline{rs1} and \asminline{rs2} (signed comparison) in \asminline{rd}.
	\item Minimum Unsigned: \asminlinehl{minu rd, rs1, rs2}: Stores the minimum of \asminline{rs1} and \asminline{rs2} (unsigned comparison) in \asminline{rd}.
	\item Sign Extend Byte: \asminlinehl{sext.b rd, rs1}: Sign-extends the least significant byte in \asminline{rs1} to 32 bits, storing result in \asminline{rd}.
	\item Sign Extend Halfword: \asminlinehl{sext.h rd, rs1}: Sign-extends the least significant halfword (16 bits) in \asminline{rs1} to 32 bits, storing result in \asminline{rd}.
	\item Zero Extend Halfword: \asminlinehl{zext.h rd, rs1}: Zero-extends the least significant halfword in \asminline{rs1} to 32 bits, storing result in \asminline{rd}.
	\item Rotate Left: \asminlinehl{rol rd, rs1, rs2}: Rotates \asminline{rs1} left by the number of bits specified in the lower 5 bits of \asminline{rs2}, storing result in \asminline{rd}.
	\item Rotate Right: \asminlinehl{ror rd, rs1, rs2}: Rotates \asminline{rs1} right by the number of bits specified in the lower 5 bits of \asminline{rs2}, storing result in \asminline{rd}.
	\item Rotate Right Immediate: \asminlinehl{rori rd, rs1, shamt}: Rotates \asminline{rs1} right by \asminline{shamt} bits, storing result in \asminline{rd}.
	\item OR Combine: \asminlinehl{orc.b rd, rs1}: Sets each byte in \asminline{rd} to 0xFF if the corresponding byte in \asminline{rs1} is nonzero, otherwise sets to 0x00.
	\item Byte Reverse: \asminlinehl{rev8 rd, rs1}: Reverses the byte order in \asminline{rs1}, storing result in \asminline{rd} (converts between big-endian and little-endian).
\end{itemize}

\subsubsection{Carryless Multiplication (Zbc)}

\begin{itemize}
	\item Carryless Multiply Low: \asminlinehl{clmul rd, rs1, rs2}: Performs carryless multiplication of \asminline{rs1} and \asminline{rs2}, storing the lower 32 bits of the result in \asminline{rd}. Useful for CRC calculations and cryptographic operations.
	\item Carryless Multiply High: \asminlinehl{clmulh rd, rs1, rs2}: Performs carryless multiplication of \asminline{rs1} and \asminline{rs2}, storing the upper 32 bits of the result in \asminline{rd}.

\end{itemize}

\section{Core Performance and Instruction Timing} \label{s:cpi}

The VestaRV core is a multi-cycle machine on a single unified instruction and data bus, but it issues the fetch of the next instruction during the execute cycle of the current one. Most instructions therefore retire at one per MCLK cycle, and the core's measured cycles-per-instruction (CPI) is much closer to 1 than the term ``multi-cycle'' on its own would suggest: over the benchmark suite of Section~\ref{ss:cpi-measured} it is 1.260. This section collects the per-instruction timings quoted throughout Section~\ref{s:cpu-instructions}, adds the classes that section does not cover, and reports the CPI actually measured on that suite.

Every figure below is for one hart executing out of its own TCM with no shared-bus contention. An access that crosses the arbiter into the shared window, or that is made while another hart holds the grant, adds stall cycles on top of these numbers (Section~\ref{s:multicore}). The core's clock is gated while it waits, so a stalled cycle is still an MCLK cycle in which nothing retires and it is charged to CPI like any other.

\subsection{Compressed Instructions and Fetch Alignment} \label{ss:cpi-align}

The core fetches one 32-bit word per bus cycle. With the C extension enabled instructions are only guaranteed 2-byte aligned, so a 32-bit instruction may straddle a word boundary, and the core must have both halves before it can decode. Compressed (2-byte) instructions and word-aligned 32-bit instructions are never affected.

The core covers most of that case in hardware, with a fetch-ahead. When it is about to step \emph{sequentially} onto a straddling 32-bit instruction, it can already see that instruction's lower half in the word it is holding, and the fetch its ordinary sequencing would issue is for the word it is holding already --- a bus cycle that would carry nothing new. The fetch-ahead spends that cycle on the \emph{next} word instead and latches the lower half at the same edge, so the straddling instruction dispatches in one cycle and costs nothing at all. The whole mechanism is one flip-flop, it issues no bus cycle the core would not have issued one cycle later, and it changes cycle counts only, never an architectural result. It is the \texttt{core.fetchAhead} knob of Table~\ref{t:chip-config} (the \texttt{ENABLE\_IF\_AHEAD} generic on the core), it is \emph{on} in this build, and turning it off is a performance choice and nothing else.

What the fetch-ahead cannot cover is a \emph{taken} control transfer whose target is a half-word-aligned 32-bit instruction. It arms only on a sequential advance, because that is the only case in which the core can prove --- from a half-word it can already see --- what it is about to fetch; after a taken branch or jump the core arrives at the target holding nothing, and genuinely needs two fetches before it can decode. That case still costs one extra cycle, and it is the whole of the residual reported below. Both rows of Table~\ref{t:cpi-timing} are measured directly: a straight-line block in which every 32-bit instruction straddles runs at 1.000 cycles per instruction, while a block of a taken branch, a straddling 32-bit target and a compressed instruction --- three instructions that cost one cycle each on their own --- takes 4 cycles.

Table~\ref{t:cpi-align} isolates what the C extension still costs by rebuilding the whole benchmark suite for RV32IMA instead of RV32IMAC. The compiler emits the identical instruction sequence in both builds --- the retired-instruction counts match exactly, benchmark for benchmark --- and only the encoding differs, so the entire difference in cycle count is the straddling-fetch penalty that survives the fetch-ahead. Across the suite it is 0.031 CPI, or 2.2\% of all cycles.

None of this is an argument against the C extension, which is configured on by default and earns its place by shrinking code substantially --- decisive when a hart's private TCM is \TcmSizeKiB{} KiB.

\subsection{Measuring Your Own Code} \label{ss:cpi-measure}

The core implements the \register{cycle}/\register{cycleh} and \register{instret}/\register{instreth} counters, and their machine-mode aliases \register{mcycle} and \register{minstret}, in every configuration. \register{cycle} counts MCLK cycles, free-running and independent of whether the core is stalled; \register{minstret} counts instructions actually retired. Bracketing a region with \asminline{rdcycle} and \asminline{rdinstret} and taking the differences therefore gives that region's exact cycle count and CPI on hardware, with no external instrumentation:

\begin{lstlisting}[style=customC]
unsigned c0, i0, c1, i1;
__asm__ volatile ("rdcycle %0; rdinstret %1" : "=r"(c0), "=r"(i0));
hot_loop();
__asm__ volatile ("rdcycle %0; rdinstret %1" : "=r"(c1), "=r"(i1));
/* cycles = c1 - c0, instructions = i1 - i0 */
\end{lstlisting}

Note that \register{time} and \register{timeh} are \emph{not} implemented in any configuration --- no real-time source is wired to the core --- and reading either raises an illegal-instruction trap. Use \register{cycle} for elapsed time, converting through the known MCLK frequency, or a timer peripheral for wall-clock measurement.

\subsection{Measurement Methodology} \label{ss:cpi-method}

The numbers in this section are measured on the RTL, not estimated. Each benchmark is run to completion in a VHDL simulation of the bare core with a one-cycle-latency memory and no bus back-pressure, which is the timing a single hart sees executing from its own TCM. Cycles are counted on the free-running core clock, so any cycle in which the core's clock is gated is still counted. Instructions are counted from the core's internal instruction-retire strobe --- the same signal that increments \register{minstret} --- so the instruction count is architectural rather than an estimate derived from the simulation. The core under measurement is configured as this build ships it, fetch-ahead included.

The per-class costs in Table~\ref{t:cpi-timing} come from paired micro-kernels: a loop containing 64 copies of the instruction under test is run against an otherwise identical empty loop, and the difference in cycles divided by the difference in retired instructions gives the marginal cost of that instruction alone, with the loop's own overhead subtracted out. Every micro-kernel body is word-aligned, so no class is charged a fetch cost that is not its own, with two deliberate exceptions: the two kernels that measure the straddling rows are built to straddle. One is a straight-line block of four instructions, two of them straddling 32-bit ones and every one of them reached sequentially, which measures 1.000 cycles per instruction; the other is a taken branch onto a straddling 32-bit target followed by a compressed instruction, three instructions whose measured classes cost one cycle each, which measures 4 cycles for the block.

\section{Forth Interpreter} \label{s:forth}
When the MCU comes out of reset and the \pin{BOOT} pin is LOW, the MCU boots to an interactive Forth interpreter based on the Forth language. Forth is a stack-based language where variables are pushed to a stack in LIFO (last in, first out) order. When a variable is set, it is pushed to the top of the stack (TOS). When a variable is used, it is popped (or consumed) from the TOS. Functions that take arguments pop them from the TOS. Functions that have return values push them to the TOS (after first popping its arguments). Variables are not assigned names, and the only way of distinguishing them from one another is by their order on the stack. All variables are treated as 32-bit signed integers. Variables may be pushed to the stack through the command line by simply typing the variable value into the interpreter as a plain text integer value or as a plain text hexadecimal value. Hexadecimal values must be preceded by the string \forthinlinehl{0x} without spaces in between (e.g. \forthinlinehl{0xA4}), but the value may be upper or lower case and does not need leading zeros. Variables are not pushed or popped and functions are not executed until a newline (or line feed) \forthinlinehl{\\n} character is received, at which point the entire received line will be executed in order. New functions may be declared, and may use the stack and any already defined functions to perform their procedures. If the Forth interpreter does not recognize an input as a variable or a function, it prints the \forthinlinehl{?} char over the UART.

The Forth interpreter contained in the ROM of the MCU communicates over \peripheral{UART0} at 115,200 baud. The baud may be changed by reconfiguring SMCLK and the \peripheral{UART0} peripheral. When the Forth interpreter first starts up, it prints the string \forthinlinehl{myshkin rv4th-rom!\\n\\n>}, and is then ready to receive characters over the UART. The Forth interpreter does not perform error handling on stack underflows. In the case of a stack underflow, it simply uses the value 0 as the TOS. By default, the echo is enabled, which repeates all characters received by the Forth interpreter back to the host. This is useful for typing into a terminal emulator manually, but may be switched off with the command \forthinlinehl{0 echo}

Several useful built-in Forth functions are listed below. The syntax is read as follows: The Forth function keyword is surrounded by quotations (though you do not actually type the quotes into the Forth interpreter), and is followed by the list of arguments and return values in parentheses. Left of the double dash is the list of arguments in the order that they would be typed into the Forth interpreter (reverse stack order), and right of the double dash is the list of return values in reverse stack order. Reverse stack order means that the rightmost item is at the TOS, and items to the left of it are below it on the stack. Arguments are always popped from the stack before the function executes, and return values are always pushed to the stack after the function finishes.

\subsection{Interpreter Limits} \label{ss:forthlimits}
The interpreter keeps all of its mutable state in the private TCM of the hart that runs it, hart 0. That TCM is 8\,KiB, of which the interrupt vector table takes the first 484 bytes and the C stack is reserved the top 1\,KiB, so the interpreter's arrays are sized to what is left. The capacities are therefore fixed by the ROM and are not configurable at run time:

\begin{itemize}
	\item Data (math) stack: 128 cells of 32 bits.
	\item Return (address) stack: 64 cells of 32 bits. Each active \forthinline{do loop} uses three of them, so loop nesting is bounded well below that.
	\item Dictionary: 64 user-defined words, 512 bytes total of word names including the separating space after each, and 1024 opcodes of compiled body shared by all of them.
	\item Input line buffer: 128 characters.
	\item Word buffer: 64 characters, so a single word name is at most 63 characters.
\end{itemize}

Only three of these are checked at run time: math stack underflow, input line overflow and word buffer overflow. Exceeding the dictionary capacities or underflowing the return stack is not detected and corrupts interpreter state. The interpreter is intended as an interactive monitor and a flash programming path, not as a development environment for large programs; a program that outgrows these limits belongs in the SPI flash boot mode described in Section~\ref{s:programming}.

Note also that the interpreter's receive path is a polled loop with no flow control. A host that delivers a line back to back at 115,200 baud can lose characters, because the interpreter echoes each character as it takes it. Typing at a terminal, or a host that leaves a character time of idle line between frames, does not.

\subsection{Creating New Forth Functions}
To create a new Forth function on-the-fly, simply use the syntax \forthinlinehl{: funcname definition ;} where \forthinline{funcname} is the name of the new function and \forthinline{definition} is the body of the function. The new function may be called at any time after the semicolon (even before a new line, though it will not actually be executed until a new line) by typing the function name, just like all other Forth functions. New Forth functions can only add or remove variables from the stack and call other defined Forth functions. The arguments to custom Forth functions are the initial values on the stack that the custom function pops off the TOS. Likewise, the return values are any new values the custom function pushes to the TOS.

Listed below is an example program that increments the TOS by one when it is called:

\subsection{Conditionals}
The \forthinlinehl{if then} functions implement a conditional statement which may only be used inside a user defined function. The conditional is used with the syntax:

\noindent\forthinlinehl{if procedureIfTrue then}

\noindent inside a function (do not forget the space and semicolon which must come after forthinline{then}). The \forthinlinehl{if} function pops the TOS and then executes whatever is defined within \forthinline{procedureIfTrue} if and only if the TOS is true (nonzero). The \forthinlinehl{then} function makrks the end of the conditional procedure. For example, a function to print the text \forthinline{cool} if the TOS is equal to 5 might look like this:

\noindent\forthinlinehl{: cool? 5 == if 108 111 111 99 emit emit emit emit then ;}

The \forthinlinehl{else} keyword may be inserted after \forthinlinehl{procedureIfTrue} if you want to execute something if the conditional is false. The syntax then becomes:

\noindent\forthinlinehl{if procedureIfTrue else procedureIfFalse then}


\subsection{Loops}
Forth has the equivalent of C-like \forthinline{while} loops (or, more accurately, \forthinline{do while} loops) with its \forthinlinehl{begin until} loops, which may only be executed inside a user defined function. The syntax is:

\noindent\forthinlinehl{begin loopProcedure until}

\noindent which first executes the loop procedure. When it gets to the \forthinlinehl{until} statement, it then checks if the TOS is true (nonzero) or false (zero). If the TOS is false, it loops back to the beginning of the loop. If true, it exits the loop and continues on.

Forth also has the equivalent of C-like \forthinline{for} loops with its \forthinlinehl{do loop} functions. Again, this may only be used inside a user defined function. It uses the syntax:

\noindent\forthinlinehl{stop start do loopProcedure loop}

\noindent where \forthinline{stop} is the index the loop stops on (it does NOT execute the loop procedure when the index is equal to \forthinline{stop}), \forthinline{start} is the first loop index, and \forthinline{loopProcedure} is any functions or variables that you want to execute inside the loop. There is a special function \forthinlinehl{i} that may only be called from within a loop which pushes the loop index to the TOS. The functions \forthinlinehl{j} and \forthinlinehl{k} behave similarly, except they return the indices of the second and third nested loops respectively when using nested loops. The \forthinlinehl{i} function always returns the index of the deepest (or most frequent) loop.

Below is an example Forth program that prints the numbers from 0 to 9 using a \forthinlinehl{do loop} procedure:

\noindent\forthinlinehl{: looptest 10 0 do i . loop ;}

\section{Software Development and Build Process} \label{s:software}

\subsection{The RISC-V Toolchain and its Extensions}
To compile software for the VestaRV CPU core, you will need the RISC-V GNU toolchain, an open source compiler suite supporting multiple programming languages. The base instruction set, RV32I (Integer), provides fundamental integer arithmetic operations, excluding multiplication, division, and modulo. All RV32I instructions are 32 bits in length without exception.

The \AsicNameForUserGuide{} MCU's VestaRV core implements several standard and extended instruction sets beyond the base RV32I:

\begin{itemize}
	\item \textbf{M Extension (Integer Multiplication and Division):} Adds hardware multiply (\asminline{mul}), divide (\asminline{div}), and modulo/remainder (\asminline{rem}) instructions with both signed and unsigned variants. Without this extension, the compiler must emulate these operations in software, significantly impacting performance.
	
	\item \textbf{A Extension (Atomic Instructions):} Provides atomic memory operations including load-reserved/store-conditional (\asminline{lr.w}/\asminline{sc.w}) and atomic read-modify-write operations (\asminline{amoadd.w}, \asminline{amoswap.w}, etc.). While primarily designed for multiprocessor synchronization, these instructions ensure atomic operations in interrupt-driven single-core systems.
	
	\item \textbf{C Extension (Compressed Instructions):} Introduces 16-bit compressed encodings for frequently used instructions, reducing program size by approximately 20-30\% according to RISC-V documentation. Uncompressed instructions on non-4-byte-aligned addresses may incur additional execution cycles. This extension significantly improves code density without sacrificing functionality.
	
	\item \textbf{Zba Extension (Address Generation):} Provides shift-and-add instructions (\asminline{sh1add}, \asminline{sh2add}, \asminline{sh3add}) optimized for efficient array indexing and pointer arithmetic, particularly beneficial for accessing elements in arrays with 2, 4, or 8-byte strides.
	
	\item \textbf{Zbb Extension (Basic Bit Manipulation):} Includes instructions for bit counting (\asminline{clz}, \asminline{ctz}, \asminline{cpop}), logical operations with inverted operands (\asminline{andn}, \asminline{orn}, \asminline{xnor}), min/max operations, sign/zero extension, rotations, and byte manipulation. These instructions accelerate bit-level algorithms, cryptographic primitives, and data packing/unpacking.
	
	\item \textbf{Zbc Extension (Carryless Multiplication):} Implements carryless multiplication instructions (\asminline{clmul}, \asminline{clmulh}, \asminline{clmulr}) essential for efficient CRC calculations, error detection codes, and certain cryptographic operations such as Galois field arithmetic.
	
	\item \textbf{Zbs Extension (Single-Bit Manipulation):} Offers single-bit set, clear, invert, and extract operations (\asminline{bset}, \asminline{bclr}, \asminline{binv}, \asminline{bext}) with both register and immediate variants, facilitating efficient manipulation of bit fields and flags.
\end{itemize}

When compiling for the \AsicNameForUserGuide{} MCU, specify the complete architecture string \\ \bashinline{-march=rv32imac\_zba\_zbb\_zbc\_zbs} to enable all supported extensions. Individual extensions may be selectively disabled by omitting them from the \bashinline{-march} flag if desired for compatibility testing or code size optimization.

\subsection{Getting the RISC-V Toolchain on Linux} \label{ss:linuxinstall}
There are two primary methods for obtaining the RISC-V toolchain on Linux: installing a prebuilt binary distribution or building from source. For most users, the prebuilt xPack distribution is recommended due to its simplicity and time savings.

\subsubsection{Option 1: Prebuilt xPack Toolchain (Recommended)}

The xPack project provides precompiled RISC-V GCC toolchains with support for all standard extensions including RV32IMAC and bit manipulation (Zb*). This is the fastest and simplest installation method.

\begin{enumerate}
\item Download the latest xPack RISC-V Embedded GCC release from:

\href{https://github.com/xpack-dev-tools/riscv-none-elf-gcc-xpack/releases}{https://github.com/xpack-dev-tools/riscv-none-elf-gcc-xpack/releases}

Select the appropriate package for your system (typically \bashinline{xpack-riscv-none-elf-gcc-*-linux-x64.tar.gz} for 64-bit Linux systems).

\item Create a directory for the toolchain and extract the archive:

\bashinlinehl{mkdir -p \~/riscv-toolchain}

\bashinlinehl{tar -xf xpack-riscv-none-elf-gcc-*.tar.gz -C \~/riscv-toolchain/}

\item Set the toolchain path as an environment variable. Add the following to your \bashinline{\~/.bashrc} or \bashinline{\~/.profile} file:

\bashinlinehl{export RISCV\_TOOLCHAIN\_DIR=\~/riscv-toolchain/xpack-riscv-none-elf-gcc-13.2.0-2}

\bashinlinehl{export PATH=\$RISCV\_TOOLCHAIN\_DIR/bin:\$PATH}

Replace \bashinline{13.2.0-2} with your downloaded version number.

\item Reload your shell configuration or open a new terminal:

\bashinlinehl{source \~/.bashrc}

\item Verify the installation:

\bashinlinehl{riscv-none-elf-gcc --version}

You should see the GCC version information confirming successful installation.
\end{enumerate}

\subsubsection{Option 2: Building from Source}

Building the toolchain from source provides maximum flexibility and ensures the latest features, but requires significantly more time and disk space. You can find the source code for the RISC-V toolchain at \href{https://github.com/riscv/riscv-gnu-toolchain}{https://github.com/riscv/riscv-gnu-toolchain}, which also contains instructions for building the toolchain. The following procedure builds a toolchain with full support for RV32IMAC and bit manipulation extensions.

First, install the required build dependencies on Ubuntu or Linux Mint:

\begin{lstlisting}[language=bash]
sudo apt install autoconf automake autotools-dev curl libmpc-dev libmpfr-dev libgmp-dev gawk build-essential bison flex texinfo gperf libtool patchutils bc zlib1g-dev libexpat-dev
\end{lstlisting}

The instructions are as follows:
\begin{enumerate}
\item Switch to your home directory with

\bashinlinehl{cd \~}
\item Make a new directory with

\bashinlinehl{mkdir riscv-download}

and go into it with

\bashinlinehl{cd riscv-download}
\item Download the RV32IMC toolchain with

\bashinline{git clone --recursive https://github.com/riscv/riscv-gnu-toolchain riscv-gnu-toolchain-rv32imc}
\item Enter into the new directory with

\bashinlinehl{cd riscv-gnu-toolchain-rv32imc}
\item Create a build directory with

\bashinlinehl{mkdir build}

Enter into the new build directory with \bashinlinehl{cd build}
\item Configure the build with

\bashinlinehl{../configure --with-arch=rv32imc --prefix=/opt/riscv/rv32imc}
\item Begin the build process with

\bashinlinehl{sudo make}

This will take quite a while. If you wish to speed up the process, you can allocate more CPU cores to the build process by using \bashinlinehl{make -jn} instead of \bashinlinehl{make} where \bashinline{n} can be replaced by the number of CPU cores you want to use to build the toolchain.). Once the build process has finished successfully, the toolchan will be located at \bashinline{/opt/riscv/rv32imc}

\item Add a permanent environment variable to your system that defines the location of the \bashinlinehl{riscv} directory (perhaps in your \bashinline{.bashrc} script) with something like

\bashinlinehl{export RISCV=/opt/riscv}

You may also wish to add the \bashinline{/opt/riscv/rv32imc/bin} directory to your PATH, though this is optional.
\item You may now safely delete the \bashinline{riscv-download} directory with

\bashinlinehl{sudo rm -rf \~/riscv-download}
\end{enumerate}



\subsection{Getting the RISC-V Toolchain on Windows}
The RISC-V toolchain has no official support for Windows, but several options exist to get it working. For Windows 10 users, it is recommended to install the Windows Subsystem for Linux (WSL) in Ubuntu mode, which can be found in the Microsoft Store app. Then, in WSL, follow the installation instructions in Section \ref{ss:linuxinstall}. You must then use WSL to compile all software for the RISC-V MCU.
If you have an older version of Windows, it is suggested that you use an Ubuntu or Linux Mint virtual machine to build the RISC-V toolchain and compile your MCU software.

\subsection{Compilation}
The RISC-V toolchain includes a GCC compiler. Thus, the compilation process is similar to other toolchains that use GCC. To compile a source file into an object file, use:

\noindent\bashinlinehl{riscv32-unknown-elf-gcc -c \$CFLAGS srcFile -o objectFile.o}

\noindent or for the xPack toolchain:

\noindent\bashinlinehl{riscv-none-elf-gcc -c \$CFLAGS srcFile -o objectFile.o}

\noindent where \bashinline{\$CFLAGS} should be replaced by any compilation flags, \bashinline{srcFile} is the source code file (C, C++, assembly, or other GCC-supported languages), and \bashinline{objectFile.o} is the output object file. The compiler determines which launguage is used in a source file by the file extension (\bashinline{.c} is for C, \bashinline{.cpp} is for C++, \bashinline{.S} is for assembly code which must be preprocessed, and \bashinline{.s} is for assembly code which is not preprocessed).

There are several compilation flags that are suggested:
\begin{itemize}
\item \bashinlinehl{-march=rv32imac\_zba\_zbb\_zbc\_zbs} Architecture flag. This specifies which ISA extensions are enabled during compilation. For the \AsicNameForUserGuide{} MCU with full VestaRV capabilities, use the complete architecture string as shown to enable the base integer instructions (I), hardware multiplication/division (M), atomic operations (A), compressed instructions (C), and all bit manipulation extensions (Zba, Zbb, Zbc, Zbs). Individual extensions may be selectively disabled by omitting them from the string (e.g., \bashinline{-march=rv32imc} for basic support without atomics or bit manipulation, or \bashinline{-march=rv32imac} to include atomics but exclude bit manipulation extensions).

\item \bashinlinehl{-mabi=ilp32} Application Binary Interface (ABI) flag. Specifies the calling convention and data model. Use \bashinline{ilp32} for integer-only ABI without floating point support, which is appropriate for the VestaRV core.

\item \bashinlinehl{-Os} Optimize for program size flag. Attempts to minimize the compiled program size, which is particularly important for memory-constrained embedded systems.

\item \bashinlinehl{-O<number>} Optimization level flag. Controls compiler optimization aggressiveness. Common values are \bashinline{-O0} (no optimization, useful for debugging), \bashinline{-O1} (basic optimizations), \bashinline{-O2} (recommended for production), \bashinline{-O3} (aggressive optimizations, may increase code size), and \bashinline{-Og} (optimize for debugging experience).

\item \bashinlinehl{-I <include\_directory>} Include directory flag. Adds the specified directory to the list of directories searched for header files. Any files in the include directory may be included with the \forthinline{\#include <filename.h>} preprocessor directive.

\item \bashinlinehl{-g} GDB debugger enable flag. Includes debugging symbols in the compiled output. Adding the \bashinline{-g} flag to both the compiler and linker commands will allow disassembly listings (\bashinline{.lst} files) to show the correspondence between source code and generated assembly instructions.

\item \bashinlinehl{-Wall -Wextra} Warning flags. Enable comprehensive compiler warnings to catch potential issues during development. The \bashinline{-Wall} flag enables common warnings, while \bashinline{-Wextra} adds additional checks.
\end{itemize}

\textbf{Example compilation command for the \AsicNameForUserGuide{} MCU:}

\begin{lstlisting}[language=bash]
riscv-none-elf-gcc -c \
  -march=rv32imac_zba_zbb_zbc_zbs \
  -mabi=ilp32 -O2 -Wall -Wextra \
  -I./include -g \
  main.c -o main.o
\end{lstlisting}

You must compile every source file that you wish to use in your project. If your project is in C or C++, it is suggested that you use the provided \bashinline{start.S} assembly file to call your main function. This assembly file needs to have its first instruction at address \texttt{\SpiFlashProgramAddress}, so it must be the first file to be given to the linker. You must have one and only one \bashinline{int main()} function throughout all of your source files in a single project. For C++ projects, you need to start the main function with \bashinline{extern "C" int main()} to prevent the C++ compiler from name-mangling the main function.


\subsection{Linking}
Once all source files have been compiled, they must be linked to produce the output program binary file, the \bashinline{.elf} file. The linker assigns memory addresses to every variable and function. The MCU contains no writable non-volatile memory, so the program and the variables all share the RAM (with a notable exception for the bootloader and Forth interpreter stored on the ROM). The linker must be aware of the RAM and ROM start address and size, the interrupt vector table (IVT) start address and size (along with the address of each ISR pointer within the IVT), the first program instruction address that the bootloader jumps to after loading the program into RAM, and the address of the master interrupt handler. 

Defining the aforementioned memory segments and addresses is done using a linker script. It is highly suggested to use the provided linker script \bashinline{MCU.ld} and its include files and tweak it to suit your need.

To execute the linker, use:

\noindent\bashinlinehl{riscv32-unknown-elf-gcc $LFLAGS $OBJECTS -o program.elf}

\noindent where \bashinline{$LFLAGS} is a list of linker flags, \bashinline{$OBJECTS} is a list of all the compiled object files needed for the project, and \bashinline{program.elf} is the output ELF binary containing the program.

There are several linker flags that are suggested:
\begin{itemize}
\item \bashinlinehl{-march=rv32imac_zba_zbb_zbc_zbs} Architecture flag. This specifies which extensions are enabled in the linking process. The VestaRV core supports the RV32IMAC instruction set plus the Zba, Zbb, Zbc, and Zbs bit manipulation extensions. This flag must match the architecture flags used during compilation.
\item \bashinlinehl{-flto} Link-time optimization flag. This instructs the linker to perform optimizations to the final binary.
\item \bashinlinehl{-nostdlib} Disables the use of the standard library for linking, decreasing software bloat. However, using the flag precludes using standard library functions such as software emulation of integer multiplication and division, floating point numbers, initialization routines, memory allocation, etc. It is suggested that you only use this flag if you have a specific need to reduce the software size.
\item \bashinlinehl{-T linker_script.ld} Path to the linker script
\item \bashinlinehl{-Map mapfile.map} Path to the output map file, which contains the symbol table for your project with their addresses
\item \bashinlinehl{-L linkerfiles_dir} Path to the linker scripts directory that contains any files that are included in the main linker script
\item \bashinlinehl{-g} GDB debugger enable flag. Adding the \bashinline{-g} flag to both the compiler and linker commands will allow the \bashinline{.lst} file to show the assembly commands your code compiles into.
\end{itemize}


\subsection{Intel Hex File Generation}
Once the final ELF file has been created from the linker, an Intel hex file can be created, which converts the binary program data into an easy-to-read ASCII file. Furthermore, the Python package \texttt{IntelHex} can read the file, allowing you to use Python to upload a new program to the SPI flash. A Python program that utilizes \texttt{IntelHex} to upload new programs, called \bashinline{forthprog.py}, is provided.


\subsection{A Note on Using C++}
C++ generates some extra data sections that C and assembly do not use. In particular, it generates the \texttt{.eh\_frame} section, which is used for exception handling. You may not need exception handling, in which case you can pass in the compiler flags:

\noindent\bashinlinehl{-fno-exceptions -fno-unwind-tables -fno-asynchronous-unwind-tables}

\noindent which will significantly reduce the size of \texttt{.eh\_frame}. If you wish to eliminate it entirely, you can create a phony section in the linker script at an unused memory address and point the \texttt{.eh\_frame} section to it.

\section{Uploading Program to SPI Flash} \label{s:programming}

\subsection{SPI Flash Boot Process}
In order to boot in SPI flash mode, there must first be a vaild program stored in the SPI flash memory in the proper location. In SPI flash mode, the bootloader reads the data in the SPI flash memory starting at address \texttt{\SpiFlashProgramAddress} and copies every 32-bit word into RAM, also starting at address \texttt{\RamStartAddress}. This particular address is the beginning of the RAM on the MCU. The bootloader stops copying from the SPI flash once completely fills the RAM.

Note the distinction between copying 32-bit words as opposed to 8-bit bytes. Though bytes and words are both MSB-first, they are also transmitted starting with the lowest address to the greatest address from the SPI flash. If the bootloader copied every 8-bit byte, the transmission sequence it would expect would be:

\noindent\texttt{byte0, byte1, byte2, byte3, byte4, byte5, byte6, byte7 ...}

\noindent However, because the bootloader expects MSB-first 32-bit words, the sequence must be:

\noindent\texttt{byte3, byte2, byte1, byte0, byte7, byte6, byte5, byte4 ...}

\noindent Therefore, the program data on the SPI flash must follow the 32-bit word sequence.

\subsection{Upload Process}
The Forth boot mode has a mechanism for writing data to the SPI flash, which may be used to upload a new program for use in the SPI flash boot mode. When in Forth boot mode, the flash write \forthinlinehl{fw} function writes a page of data (which is exactly 256 bytes long and begins on an address that is a multiple of 256) to the SPI flash. The Forth function is used with the syntax:

\noindent\forthinlinehl{bin addr fw}

If \forthinline{bin} is true (nonzero), the command expects 256 bytes of binary data to be transmitted over the UART. If false, it expects a 512-character long ASCII hex string representing the data to be transmitted over the UART. The \forthinline{addr} argument must be the address of the beginning of the 256-byte page, and must be aligned to a 256-byte boundary.

To execute the command, a newline (or line feed) character must be transmitted to the MCU over the UART. Once the command begins executing, it initiates some handshaking to ensure a proper transaction. The MCU prints a \forthinline{\$} character to indicate it is ready for the page data to be transmitted. After that, you must transmit the page data in the format specified by the \forthinline{bin} argument. Remember to transmit the data in the proper order (byte3, byte2, byte1, byte0, byte7, byte6, byte5, byte4 ...). Once the page data has been transmitted, the MCU will compute a CRC value upon the data using the CRC16\_CDMA2000 algorithm (polynomial = 0xC857, initial CRC value = 0xFFFF, no final XOR, no data reflection, no output reflection) and then transmit the CRC value as a 4-character long hex string. If this value matches your own CRC computation (or if you do not care and simply want it to write the data), transmit a single \forthinline{Y} character without anything else to tell the MCU to write the data to the SPI flash. Any other character will abort the process, leaving the SPI flash memory unchanged. You are technically supposed to wait an average of 10 ms (25 ms at the greatest) before writing more data to the SPI flash. However, the substantial handshaking and transmission times likely fulfill this requirement, and it is likely that no delay is needed.

If the entire page is blank, you may instead use the flash erase \forthinlinehl{fe} function to erase the page, making every byte in the page equal to 0xFF. This is much quicker than writing data to the SPI flash, and can speed up programming times substantially for smaller programs. The syntax to use it is:

\noindent\forthinlinehl{conf addr fe}

If the \forthinline{conf} parameter is equal to 123, the function will erase the 256-byte page at address \forthinline{addr} (which must be 256-byte aligned) and then return 1. If not equal to 123, it will not erase the page and will return 0. You are technically supposed to wait an average of 6~ms (25~ms at the greatest) before another erase or write operation. Because the erase function is much quicker than the write function, it may become necessary to delay between erases at higher bauds.

You may read back the data stored on the SPI flash with the \forthinlinehl{fr} function. See Section \ref{ss:forthflash} for details.

In order to write an entire program to the SPI flash, you must write/erase a total of \RamNumPages\ pages (each with a length of 256 bytes) beginning with page address \RamStartAddress. After the data is written, you may execute the newly uploaded program by putting the MCU in reset, setting the \pin{BOOT} pin to SPI flash mode, and taking the chip out of reset. Or, you can simply set the \pin{BOOT} pin and move the program counter to address 0x0000, which may be done with the \forthinlinehl{rst} Forth function.

It is highly suggested to use the provided Python program \bashinline{forthprog.py} to upload new programs to the SPI flash, which takes an Intel hex file containing the new program and sends it to the MCU and the SPI flash using the process described above.
