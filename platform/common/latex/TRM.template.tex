\section{Scope and audience}

This manual is the technical reference for the \AsicNameForUserGuide{} microcontroller. It is written for firmware developers and board designers, and it assumes familiarity with 32-bit microcontrollers, memory-mapped peripherals and the RISC-V instruction set. It describes the hardware as implemented: the address map, every peripheral and its registers, the interrupt fabric, the boot ROM and the processor core's configuration. The RISC-V specifications are normative for the instruction set and for the privileged architecture; where this manual restates them it does so only to say which parts are implemented and how. Where the implementation deviates from a specification, the deviation is stated where it applies.

Everything in this manual is generated from one chip configuration, the same one that produces the RTL, the C headers and the linker scripts (Section~\ref{ss:chipConfig}), so a value printed here is the value built.

\section{Organisation of this manual}

\begin{description}[style=nextline, leftmargin=0pt, itemsep=2pt]
	\item[Part I, System] What is on the chip, its package and pins, the address map, the multi-core architecture, and reset, clocks and power. Read this part first.
	\item[Part II, Processor] The VestaRV core: its instruction set, control and status registers, privileged architecture, interrupts and exceptions, instruction timing, and the debug system.
	\item[Part III, Peripherals] One chapter per peripheral, each with a functional description, a programming sequence, usage notes and the complete register description.
	\item[Part IV, Analog front end] The mixed-signal front end and its characterisation.
	\item[Part V, Boot ROM and software] The ROM monitor and the boot image format the boot ROM loads.
	\item[Appendices] A software development quick start, the register index, errata, and the revision history of this document.
\end{description}

\section{Conventions} \label{ss:conventions}

\begin{description}[style=nextline, leftmargin=0pt, itemsep=2pt]
	\item[Numbers] Hexadecimal numbers carry the prefix \texttt{0x} (\texttt{0x4600}); binary numbers carry the prefix \texttt{0b} (\texttt{0b101}); decimal numbers have no prefix. A value of the form \texttt{0x8000 + 4n} is an address formula in which $n$ is the array index.
	\item[Units] Capacities are binary: 1 KiB is 1024 bytes. Rates and frequencies are decimal: 115,200 baud, 24 MHz. A word is 32 bits, a half-word 16 bits and a byte 8 bits.
	\item[Registers and fields] A register is named by its peripheral template and register name, and a field by the dotted form \texttt{PERIPHERAL.\allowbreak REGISTER.\allowbreak FIELD}, for example \register{TIMx.TIMxCR.TEN}. In prose, register names are the template form (\register{PxIN}, \register{TIMxCR}), where \texttt{x} stands for the instance number; the instance form (\register{P0IN}, \register{TIM0CR}) appears only in the per-instance address tables and in the generated headers.
	\item[Bit ranges] Bits are numbered from 0 at the least significant end. A range is written \texttt{[h:l]} with the high bit first; \texttt{[7:4]} is four bits. A single bit is written \texttt{[n]}.
	\item[Set and clear] A bit is set when it holds 1 and cleared when it holds 0. Asserted means the active level of a signal, whatever its polarity; an active-low pin is named with a trailing \texttt{N} (\pin{RESETN}).
	\item[Reserved] A reserved bit reads as zero and must be written as zero. No exception is raised by an access to a reserved bit or to a reserved register offset inside a peripheral's window.
	\item[Register width] Every register is described at its natural width, 8 or 32 bits, and every register occupies one 4-byte slot at a 4-byte aligned offset regardless of its width; the unused upper bytes of an 8-bit register are reserved.
	\item[Narrow accesses] The bus carries four byte-lane write strobes, so a byte or half-word store reaches the peripheral with only the addressed lanes asserted. Reads always return the full word of the addressed slot. Whether a partial write is honoured is a property of the register: an 8-bit register lives in byte lane 0, and a register described as requiring a full-word write commits only stores that assert lane 0.
\end{description}

\begin{description}[style=nextline, leftmargin=0pt, itemsep=1pt]
	\item[Heading] The register's template name and a short title. The heading appears in the chapter's own register list, not in the main table of contents. The \texttt{x} in the name is the instance number.
	\item[Offset, Reset, Width] The byte offset from the instance base address (the base addresses are in the chapter's instance table), the reset value of the whole register, and its width in bits.
	\item[Summary sentence] What the register is for, in one to three sentences, with a pointer to the functional description for anything longer.
	\item[Field rows] One row per field, most significant first, every bit covered. \textbf{Bits} is the range, \textbf{Field} the name used in prose and in the generated headers (with the peripheral's field prefix), \textbf{Type} the access type of Table~\ref{t:access-types}, \textbf{Reset} the field's reset value at the field's width.
	\item[Enumerated values] Listed inside the description cell as \texttt{value} = \texttt{SYMBOL}: meaning. The symbol is the macro name in the generated header. Values are binary for fields of four bits or fewer and hexadecimal for wider fields.
	\item[Reserved runs] Consecutive reserved bits are collapsed into one row whose field, type and reset are a dash.
\end{description}

\section{Chip configuration} \label{ss:chipConfig}

This document, the memory-map headers, the linker scripts, and the drop-in RTL are all generated from one chip configuration by \texttt{make chip}. The configuration is a small JSON document (every key optional; a missing key keeps the \AsicNameForUserGuide{} default) passed as \texttt{make chip CONFIG=config.json}; an interactive front end for producing it ships with the generator (\texttt{docs/chip\_configurator.html}). The resolved configuration is also written to \texttt{config/ChipConfig.resolved.json} at every build, and \texttt{make verify [CONFIG=config.json]} proves a configuration by staging the generated RTL into a behavioural simulation environment and running the multi-core boot and ISA smoke suite against it. The core peripheral set and the pad ring are not configuration knobs; they are fixed template content, and the pad ring (Chapter~\ref{s:pinsConfig}) is derived from the generator's package model. The second-instance peripherals (\peripheral{UART1}, \peripheral{SPI1}, \peripheral{TIMER1}, \peripheral{I2C1}) and the \peripheral{NPU} are individually droppable through the \texttt{peripherals} section: a dropped instance's register window reads zero, its interrupt vectors are reserved (the numbering is frozen), and its pins revert to plain GPIO.

\section{GPIO pins and alternate functions}

Most of the digital I/O pins are GPIO pins. A GPIO pin is in either primary (GPIO) mode or alternate function (peripheral) mode; see the \peripheral{GPIOx} chapter (Chapter~\ref{peripheralGPIOx}). Table~\ref{t:gpio-pins} lists every GPIO pin with its primary function, its reset-selected alternate function (AF0), and the reset state of its \register{PxSEL}, \register{PxOUT}, \register{PxDIR}, and \register{PxREN} bits. The remaining alternate functions each pin can select (AF1 to AF7) are in the alternate-function matrix, Table~\ref{t:gpio-afs}.

\input{include/GpioPinsConfigurationTable.tex}

When a pin is in alternate function mode (its \register{PxSEL} bit is 1), its 3-bit \register{PxAFS} field selects which of up to eight alternate functions (AF0 to AF7) drives the pad. Table~\ref{t:gpio-afs} lists, for every GPIO pin, the function selected by each \register{PxAFS} value. Plane 0 is the pin's AF0 function and is the reset selection; planes marked \textbf{Hi-Z} have no function assigned for that pin and configure the pad as a high-impedance input. The superscript on each function denotes its direction (\textsuperscript{\scriptsize in} input, \textsuperscript{\scriptsize out} output, \textsuperscript{\scriptsize io} bidirectional), and a \textsuperscript{$\dagger$} marks each pin's reset plane (its \register{PxAFS} reset value). While a pin is in primary mode the selected plane has no effect on the pad, but it still routes relocatable peripheral inputs (Chapter~\ref{peripheralGPIOx}).

The 32-bit memory bus is a single von Neumann address space: the ROM, the RAMs and the memory-mapped peripheral registers are all reached through one bus, and a pointer can address any of them. An access to an unmapped address reads zero, and a write to one is ignored; no bus error is raised.

The ROM holds the boot loader and the ROM monitor and is read-only. Each RAM can be read and written and may hold both code and data. The chip carries no on-die non-volatile memory: it boots from an external SPI flash device, and hart 0, and only hart 0, can additionally read that flash directly, and execute in place from it, through the extended-flash window at \texttt{\FlashBaseAddress} and above (the last region in Figure~\ref{fig:address-space}; see Section~\ref{ss:spi-flash-xip}). At reset every hart fetches from the boot ROM at \texttt{\RomStartAddress} and dispatches on its hart ID: hart 0 copies the application image out of the flash into memory and enters it, and the remaining harts park until hart 0 loads and launches them (Section~\ref{ss:multicore-boot}). Each RAM and ROM block can be individually powered off and on through the \peripheral{SYSTEM} peripheral; a block that is powered off draws less static power, does not respond, and a RAM loses its contents.

\section{Reset}

The chip is held in reset while the \pin{RESETN} pin is low and leaves reset when it is released high. A power-on reset circuit asserts the internal reset while the core supply rises from zero and releases it once the supply has reached its operating level; the chip is in reset whenever either \pin{RESETN} or the power-on reset is asserted. In reset, every memory-mapped register and every core state register is at its reset value. The \pin{RESETN} input has an internal pull-up and may be left unconnected.

Every hart leaves reset fetching from the boot ROM at \texttt{\RomStartAddress}. Hart 0 runs the boot loader; harts 1 to \MaxHartIndex{} park in the ROM until hart 0 releases them through the boot mailboxes in shared RAM (Section~\ref{ss:multicore-boot}). The \peripheral{PWRCTRL} boot gate can hold every hart in reset until a supply supervisor reports power good; see Section~\ref{s:powerdomains} and Chapter~\ref{peripheralPWRCTRL}.

\chapter{VestaRV core} \label{s:cpu-instructions}
% ---------------------------------------------------------------------------

Every hart of the \AsicNameForUserGuide{} MCU is a VestaRV core, a 32-bit RISC-V processor with a single unified instruction and data bus. This chapter states what the core implements: its instruction set, its register conventions, its hart identities and its control and status registers. The RISC-V specifications named in Section~\ref{ss:related} are normative for the instructions and registers themselves and are not restated here.

\section{Instruction set} \label{ss:isa}

The ISA string of this build, the \texttt{-march} value the toolchain is given, is listed under \emph{ISA string} in Table~\ref{t:chip-config-derived}\ifdefined\IsaString{} and is \texttt{\IsaString}\fi. The same information is available at run time in the read-only \register{misa} register (Section~\ref{ss:csrs}). The extensions the core family implements are listed below with the configuration knob that selects each; which ones are present in this build is exactly what the ISA string says.

\begin{itemize}[itemsep=1pt]
	\item \textbf{RV32I}, the base integer instruction set: 32 registers of 32 bits, integer arithmetic, logic, shifts, comparisons, loads and stores of bytes, half-words and words, branches and jumps. Always present.
	\item \textbf{M} (\texttt{isa.mul}, \texttt{isa.div}): hardware multiply, divide and remainder, signed and unsigned. Multiply is single-cycle; divide is iterative (Chapter~\ref{s:cpi}).
	\item \textbf{A} (\texttt{isa.atomics}): load-reserved and store-conditional, and the atomic read-modify-write operations on 32-bit words. An atomic operation holds the shared-window arbiter grant across its whole read-modify-write pair, so it is atomic with respect to every hart (Section~\ref{ss:multicore-sync}).
	\item \textbf{C} (\texttt{isa.compressed}): 16-bit encodings of the most common instructions. Code built with it is substantially smaller; its fetch-alignment cost is measured in Section~\ref{ss:cpi-align}.
	\item \textbf{Zba, Zbb, Zbc, Zbs} (\texttt{isa.bitmanip}): address generation (shift-and-add), basic bit manipulation (count, min and max, rotate, sign and zero extension, byte reversal), carry-less multiplication, and single-bit set, clear, invert and extract.
	\item \textbf{Zicsr}: the CSR access instructions. Always present.
	\item \textbf{Zicntr}: the \register{cycle} and \register{instret} counters, readable from the user views. Always present; \register{time} is not implemented (Section~\ref{ss:csrs}).
\end{itemize}

An instruction of an extension that is not configured into the build raises an illegal-instruction exception; what happens next depends on the trap delivery mode (Section~\ref{ss:csr-unimplemented}).

Three instructions are specific to this core and are used by the runtime: \asminline{retirq} returns from a legacy-mode interrupt (Chapter~\ref{s:interrupts}), \asminline{sleep} gates the hart's clock until an interrupt arrives (Section~\ref{ss:sleep}), and \asminline{wake} is its counterpart. Their encodings are in the generated \texttt{periph.S}.

\chapter{Interrupts and exceptions} \label{s:interrupts}
% ---------------------------------------------------------------------------

The VestaRV CPU implements an interrupt system with \VectorsCount{} interrupt vectors, numbered 0 to \TopVector, whose sources are enumerated in Table~\ref{t:interrupt-vectors}. The numbering is frozen: a vector belongs to the block that owns it whether or not this configuration instantiates that block, so vectors whose block is absent are reserved and counted with the rest rather than shifting the ones above them. Two of the \VectorsCount{} are the \peripheral{CLINT} pair (\ClintMsipVector, the software or inter-processor interrupt; \ClintMtipVector, the timer interrupt) added for multi-core operation; the other \RoutedVectorsCount{} sit on the \peripheral{IRQROUTER} side of the fabric: the peripheral and system sources, the reserved slots frozen among them, and \texttt{meip}'s own slot. Each hart takes three interrupt lines: its own \peripheral{CLINT} software and timer interrupts (vectors \ClintMsipVector{} and \ClintMtipVector, hardwired enabled, delivered on dedicated per-hart wires) and the external interrupt \texttt{meip} (vector \MeipVector, a slot of its own that no source pends on), which delivers all peripheral and system sources through the \peripheral{IRQROUTER}'s claim and complete mechanism: the vector-\MeipVector{} handler reads the router's \register{CLAIM} register to discover and claim the pending source, dispatches on the returned vector number, and writes it back to complete (Chapter~\ref{peripheralIRQROUTER}). Which sources reach which hart is programmed per hart in the router's routing rows, identical for every hart, hart 0 included. All peripheral sources are masked at reset and must be routed in software before use; source priority is fixed (the lowest pending vector number is claimed first). A peripheral must additionally be configured to generate its interrupt at the peripheral level.

\section{Interrupt vector table}

The interrupt vector table (IVT) is located at the base of each hart's TCM, beginning at address \texttt{\VectorsStartAddress}. Unlike a pointer-based vector table, the VestaRV IVT contains direct jump instructions to the interrupt service routines (ISRs): each entry is a 4-byte RISC-V jump instruction (for example \asminline{j handler}) that vectors execution immediately to the corresponding ISR when an interrupt occurs. This eliminates the indirection of loading a function pointer and gives a deterministic, low-latency interrupt response.

The hardware does not mandate a specific IVT content, so software populates the IVT with jump instructions during initialisation. The generated linker scripts and startup code place the IVT at the beginning of the TCM, and the generated header files provide macros for ISR placement and IVT entry configuration.

\section{Interrupt entry, exit and recursion}

When an interrupt is taken, the hardware saves a minimal context: it pushes the return program counter (one 32-bit word) onto the stack at $\mathtt{sp}-4$, decrements \asminline{sp} by 4, and vectors execution through the IVT entry for the interrupt. No other state is saved by hardware. Software is responsible for saving and restoring every general-purpose register the ISR uses. The generated runtime provides an interrupt entry wrapper (in the startup code) that saves the general-purpose registers on the stack (about 120 bytes per interrupt level), calls the C-level handler, restores the registers, and returns with the \asminline{retirq} instruction, so C-coded ISRs need no special handling. Hand-written assembly ISRs must perform the equivalent save and restore themselves. Executing \asminline{retirq} pops the hardware-saved program counter, increments \asminline{sp} by 4, and resumes execution at the interrupted location.

\begin{Caution}
Because the first thing interrupt entry does is a store at $\mathtt{sp}-4$, the stack pointer must point at valid, writable private memory before interrupts are enabled. This applies to every hart: a freshly released tile hart must load its stack pointer before unmasking interrupts or going to sleep (Chapter~\ref{s:multicore}).
\end{Caution}

Interrupt handling is non-recursive: a running ISR is never preempted, and further pending interrupts (including a pending \peripheral{CLINT} interrupt during a vector-\MeipVector{} service) are taken after the current ISR returns. Stack allocation must cover one interrupt level: the 4-byte hardware-saved return address plus the handler's register frame (about 120 bytes for the runtime wrapper) and the ISR's local variables. Source arbitration happens in the \peripheral{IRQROUTER}; the core itself has no priority tiers.

\section{Sleep mode and interrupt wake-up}

If an interrupt occurs while the CPU is in sleep mode, the processor wakes from sleep and services the interrupt. On execution of the \asminline{retirq} instruction, the CPU returns to sleep mode unless the ISR or the woken code reconfigures the clock and power settings. During sleep mode the CPU clock is gated to conserve power, and all register contents and the program counter are retained. If the clock source for MCLK is disabled during sleep, an enabled interrupt powers up and enables the source clock for the duration of interrupt servicing.

Clock and power management, including sleep mode configuration, are controlled through the \peripheral{SYSTEM} peripheral (Section~\ref{ss:sleep}). If SMCLK is disabled, peripherals in the SMCLK domain cannot assert their interrupts and cannot wake the CPU.

\chapter{Core performance and instruction timing} \label{s:cpi}
% ---------------------------------------------------------------------------

The VestaRV core is a multi-cycle machine on a single unified instruction and data bus, but it issues the fetch of the next instruction during the execute cycle of the current one. Most instructions therefore retire at one per MCLK cycle, and the core's measured cycles-per-instruction (CPI) is much closer to 1 than the term ``multi-cycle'' on its own would suggest: over the benchmark suite of Section~\ref{ss:cpi-measured} it is 1.260. This chapter gives the cost of every instruction class and reports the CPI measured on that suite.

Every figure below is for one hart executing out of its own TCM with no shared-bus contention. An access that crosses the arbiter into the shared window, or that is made while another hart holds the grant, adds stall cycles on top of these numbers (Chapter~\ref{s:multicore}). The core's clock is gated while it waits, so a stalled cycle is still an MCLK cycle in which nothing retires and it is charged to CPI like any other.

\section{Compressed instructions and fetch alignment} \label{ss:cpi-align}

The core fetches one 32-bit word per bus cycle. With the C extension enabled instructions are only guaranteed 2-byte aligned, so a 32-bit instruction may straddle a word boundary, and the core must have both halves before it can decode. Compressed (2-byte) instructions and word-aligned 32-bit instructions are never affected.

The core covers most of that case in hardware, with a fetch-ahead. When it is about to step sequentially onto a straddling 32-bit instruction, it can already see that instruction's lower half in the word it is holding, and the fetch its ordinary sequencing would issue is for the word it is holding already, a bus cycle that would carry nothing new. The fetch-ahead spends that cycle on the next word instead and latches the lower half at the same edge, so the straddling instruction dispatches in one cycle and costs nothing at all. The whole mechanism is one flip-flop, it issues no bus cycle the core would not have issued one cycle later, and it changes cycle counts only, never an architectural result. It is the \texttt{core.fetchAhead} knob of Table~\ref{t:chip-config} (the \texttt{ENABLE\_IF\_AHEAD} generic on the core), it is on in this build, and turning it off is a performance choice and nothing else.

What the fetch-ahead cannot cover is a taken control transfer whose target is a half-word-aligned 32-bit instruction. It arms only on a sequential advance, because that is the only case in which the core can prove, from a half-word it can already see, what it is about to fetch; after a taken branch or jump the core arrives at the target holding nothing, and genuinely needs two fetches before it can decode. That case still costs one extra cycle, and it is the whole of the residual reported below. Both rows of Table~\ref{t:cpi-timing} are measured directly: a straight-line block in which every 32-bit instruction straddles runs at 1.000 cycles per instruction, while a block of a taken branch, a straddling 32-bit target and a compressed instruction (three instructions that cost one cycle each on their own) takes 4 cycles.

Table~\ref{t:cpi-align} isolates what the C extension still costs by rebuilding the whole benchmark suite for RV32IMA instead of RV32IMAC. \section{Measuring application code} \label{ss:cpi-measure}

The core implements the \register{cycle}/\register{cycleh} and \register{instret}/\register{instreth} counters, and their machine-mode aliases \register{mcycle} and \register{minstret}, in every configuration. \register{cycle} counts MCLK cycles, free-running and independent of whether the core is stalled; \register{minstret} counts instructions actually retired. Bracketing a region with \asminline{rdcycle} and \asminline{rdinstret} and taking the differences therefore gives that region's exact cycle count and CPI on hardware, with no external instrumentation:

\begin{lstlisting}[style=customC]
unsigned c0, i0, c1, i1;
__asm__ volatile ("rdcycle %0; rdinstret %1" : "=r"(c0), "=r"(i0));
hot_loop();
__asm__ volatile ("rdcycle %0; rdinstret %1" : "=r"(c1), "=r"(i1));
/* cycles = c1 - c0, instructions = i1 - i0 */
\end{lstlisting}

\register{time} and \register{timeh} are not implemented in any configuration, because no real-time source is wired to the core, and reading either raises an illegal-instruction trap. Use \register{cycle} for elapsed time, converting through the known MCLK frequency, or a timer peripheral for wall-clock measurement.

\section{Measurement methodology} \label{ss:cpi-method}

The numbers in this chapter are measured on the RTL, not estimated. Each benchmark is run to completion in a VHDL simulation of the bare core with a one-cycle-latency memory and no bus back-pressure, which is the timing a single hart sees executing from its own TCM. Cycles are counted on the free-running core clock, so any cycle in which the core's clock is gated is still counted. Instructions are counted from the core's internal instruction-retire strobe, the same signal that increments \register{minstret}, so the instruction count is architectural rather than an estimate derived from the simulation. The core under measurement is configured as this build ships it, fetch-ahead included.

The per-class costs in Table~\ref{t:cpi-timing} come from paired micro-kernels: a loop containing 64 copies of the instruction under test is run against an otherwise identical empty loop, and the difference in cycles divided by the difference in retired instructions gives the marginal cost of that instruction alone, with the loop's own overhead subtracted out. Every micro-kernel body is word-aligned, so no class is charged a fetch cost that is not its own, with two deliberate exceptions: the two kernels that measure the straddling rows are built to straddle. One is a straight-line block of four instructions, two of them straddling 32-bit ones and every one of them reached sequentially, which measures 1.000 cycles per instruction; the other is a taken branch onto a straddling 32-bit target followed by a compressed instruction, three instructions whose measured classes cost one cycle each, which measures 4 cycles for the block.

\chapter{ROM monitor} \label{s:forth}
% ---------------------------------------------------------------------------

When the chip leaves reset with the \pin{P0.7} strap low (Section~\ref{ss:bootmode}), hart 0 runs the ROM monitor: an interactive Forth interpreter stored in the boot ROM that communicates over \peripheral{UART0} at 115,200 baud, 8 data bits, no parity, one stop bit. The monitor is a bring-up console and the flash programming path of Chapter~\ref{s:programming}; it is not a development environment.

% The banner is printed by software/bootrom_mp/src/rv4th.c as
% ASIC_NAME " rv4th-rom!", with ASIC_NAME from software/commune/include/myshkin.h.
% The leading word is therefore the name compiled into that header, not this
% chip's name, and the manual does not quote it.
On start-up the monitor prints a one-line banner ending in \forthinline{rv4th-rom!}, an empty line, and the prompt \forthinline{>}, and is then ready to receive characters. The leading word of the banner is the \texttt{ASIC\_NAME} string compiled into the ROM source and does not name this chip.

\section{Interpreter model}

Forth is a stack language. Every value is a 32-bit signed integer on one data stack, the top of which is called TOS. Typing a number pushes it: a plain decimal integer, or a hexadecimal value with the prefix \forthinline{0x} in either case and without leading zeros (\forthinline{0xA4}). Typing a word (a function name) executes it; a word pops its arguments from the stack and pushes its results. Nothing is executed until a line feed is received, at which point the whole line is executed left to right. An input the interpreter does not recognise as a number or a word prints \forthinline{?}. Stack underflow is not an error: a pop from an empty stack yields 0.

By default the monitor echoes every received character back to the host, which suits a terminal emulator; \forthinline{0 echo} switches the echo off for a programmatic host.

Arguments are popped before the word executes and results are pushed after it finishes.

\section{Interpreter limits} \label{ss:forthlimits}

The interpreter keeps all of its mutable state in hart 0's TCM, of which the interrupt vector table takes the first \VectorsCount{} words and the top 1 KiB is reserved for the C stack; the interpreter's arrays are sized to what is left. The capacities are fixed by the ROM and are not configurable at run time:

\begin{itemize}[itemsep=1pt]
	\item Data (math) stack: 128 cells of 32 bits.
	\item Return (address) stack: 64 cells of 32 bits. Each active \forthinline{do loop} uses three of them, so loop nesting is bounded well below that.
	\item Dictionary: 64 user-defined words, 512 bytes total of word names including the separating space after each, and 1024 opcodes of compiled body shared by all of them.
	\item Input line buffer: 128 characters.
	\item Word buffer: 64 characters, so a single word name is at most 63 characters.
\end{itemize}

Only three of these are checked at run time: math stack underflow, input line overflow and word buffer overflow. Exceeding the dictionary capacities or underflowing the return stack is not detected and corrupts interpreter state. A program that outgrows these limits belongs in the SPI flash boot mode of Chapter~\ref{s:programming}.

\begin{Caution}
The monitor's receive path is a polled loop with no flow control, and it echoes each character as it takes it. A host that delivers a line back to back at 115,200 baud can lose characters; a host that leaves one character time of idle line between frames does not.
\end{Caution}

\section{Defining words}

A new word is defined with \forthinline{: name body ;}, where \forthinline{body} is any sequence of numbers and words. The new word may be used as soon as the semicolon has been read, even later on the same line. A user-defined word can only push and pop the stack and call other words. For example, a word that increments the TOS:

\noindent\forthinlinehl{: inc 1 + ;}

\section{Conditionals}

\forthinline{if} and \forthinline{then} form a conditional and may only be used inside a word definition. \forthinline{if} pops the TOS and executes the words up to the matching \forthinline{then} only when the popped value is nonzero. An \forthinline{else} clause is optional:

\noindent\forthinlinehl{cond if wordsIfTrue else wordsIfFalse then}

\noindent For example, a word that prints \forthinline{cool} when the TOS equals 5:

\noindent\forthinlinehl{: cool? 5 == if 108 111 111 99 emit emit emit emit then ;}

\section{Loops}

Two loop forms exist, and both may only be used inside a word definition. \forthinline{begin ... until} executes its body, then pops the TOS at \forthinline{until} and repeats the body while the popped value is zero. \forthinline{stop start do ... loop} is a counted loop: it runs its body with the index taking the values \forthinline{start} to \forthinline{stop - 1}. Inside a counted loop the word \forthinline{i} pushes the index of the innermost loop, and \forthinline{j} and \forthinline{k} the indices of the two enclosing loops. For example, a word that prints the numbers 0 to 9:

\noindent\forthinlinehl{: looptest 10 0 do i . loop ;}

When the \pin{P0.7} strap is high at reset (Section~\ref{ss:bootmode}), hart 0's boot loader reads a boot image from the SPI flash on \peripheral{SPI0}, copies its segments into RAM and enters it. The image is a stream of 32-bit words beginning at flash offset \texttt{0x000000}, read with one continuous high-frequency read command. Table~\ref{t:boot-image} is the authoritative description of the stream.

\begin{tabularx}{\textwidth}{l p{4.4cm} X}

\hline \textbf{Command word} & \textbf{Following words} & \textbf{Effect} \\ \hline \endfirsthead
\hline \textbf{Command word} & \textbf{Following words} & \textbf{Effect} \\ \hline \endhead
\texttt{0x10ADBEEF} & \texttt{START}, \texttt{END}, then $(\mathtt{END}-\mathtt{START})/4$ data words & Load segment: the data words are stored to RAM at \texttt{START}, \texttt{START + 4}, \dots, \texttt{END - 4}. \texttt{END} is exclusive. \\

\end{tabularx}

Every segment must lie inside the load window: \texttt{\RamStartAddress} $\le$ \texttt{START} $<$ \texttt{END} $\le$ \texttt{\SharedRamEndAddress} + 1, which spans the private TCM, the NPU staging RAM and the shared RAM. A segment outside the window, or any other command word, traps the boot loader. The entry address is the word at \texttt{0x10640} in shared RAM if the image has loaded a nonzero value there, and \texttt{\SpiFlashProgramAddress} otherwise; the loader zeroes the shared-RAM mailbox region before reading the flash, so an image that publishes nothing enters at \texttt{\SpiFlashProgramAddress}.

Words are transferred most-significant byte first: the flash byte at offset $4k$ is bits 31:24 of word $k$. A tool that writes the flash from a little-endian memory image must therefore reverse the byte order within every word.

A standard image, as produced by the build scripts, consists of a fill or load segment that zeroes the vector table region \texttt{\RamStartAddress} to \texttt{\SpiFlashProgramAddress}, one load segment per contiguous run of nonzero program words (a run of eight or more zero words separates segments, and each segment is padded by two trailing zero words), and the execute word. The image's first instruction is at \texttt{\SpiFlashProgramAddress} in the TCM unless it publishes an entry address; an image larger than the TCM executes from the shared RAM and publishes its entry there. The vector table itself is written by the image's startup code.

\section{Programming the flash from the ROM monitor}

The ROM monitor (Chapter~\ref{s:forth}) writes, erases and reads the flash in 256-byte pages, and the provided \texttt{forthprog.py} script (Appendix~\ref{s:software}) drives it to program a whole image from an Intel hex file. The image occupies flash pages from offset \texttt{0x000000} upward, as many as its length requires.

\begin{description}[style=nextline, leftmargin=0pt, itemsep=2pt]
	\item[\texttt{bin addr fw}] Writes one page at flash address \forthinline{addr}, which must be a multiple of 256. If \forthinline{bin} is nonzero the monitor expects 256 bytes of binary data; if zero, a 512-character ASCII hex string. After the line feed the monitor prints \forthinline{\$} when it is ready for the data. When the data has arrived it prints the CRC of the page as four hex characters (CRC16/CDMA2000: polynomial \texttt{0xC857}, initial value \texttt{0xFFFF}, no final XOR, no reflection). The host answers with a single \forthinline{Y} to commit the write; any other character aborts it and leaves the flash unchanged.
	\item[\texttt{conf addr fe}] Erases the page at \forthinline{addr} to \texttt{0xFF} when \forthinline{conf} equals 123 and pushes 1; otherwise does nothing and pushes 0. Erasing is faster than writing and is the right way to handle a blank page.
	\item[\texttt{fr}] Reads the flash back; see Section~\ref{ss:forthflash}.
\end{description}

\begin{Note}
The flash device specifies a page program time of up to 25 ms (typically 10 ms) and a page erase time of up to 25 ms (typically 6 ms). The handshake of \forthinline{fw} is long enough that no extra delay is needed between writes; consecutive erases at a high baud rate may need one.
\end{Note}

After the image is written, the chip runs it after a reset with the \pin{P0.7} strap high. The \forthinline{rst} word restarts hart 0 at the boot ROM without a pin reset, so a host that controls the strap can switch modes without toggling \pin{RESETN}.

\chapter{Software development quick start} \label{s:software}

This appendix lists the commands needed to build a program for the \AsicNameForUserGuide{} MCU and load it into the SPI flash. The memory map header, the linker script fragments and the startup code are generated by \texttt{make chip} (Section~\ref{ss:related}).

\section{Toolchain} \label{ss:linuxinstall}

The RISC-V GNU toolchain is required. The prebuilt xPack distribution supports every extension the core implements and is the quickest route on Linux; Windows users run the same steps under the Windows Subsystem for Linux.

\begin{enumerate}[itemsep=1pt]
	\item Download the current release archive (\texttt{xpack-riscv-none-elf-gcc-*-linux-x64.tar.gz}) from \url{https://github.com/xpack-dev-tools/riscv-none-elf-gcc-xpack/releases}.
	\item Extract it and export its location; the version number in the path is the one downloaded:
\begin{lstlisting}[language=bash]
mkdir -p ~/riscv-toolchain
tar -xf xpack-riscv-none-elf-gcc-*.tar.gz -C ~/riscv-toolchain/
export RISCV_TOOLCHAIN_DIR=~/riscv-toolchain/xpack-riscv-none-elf-gcc-13.2.0-2
export PATH=$RISCV_TOOLCHAIN_DIR/bin:$PATH
\end{lstlisting}
	The two \texttt{export} lines belong in the shell profile (\texttt{\~{}/.bashrc} or \texttt{\~{}/.profile}). The build system requires \texttt{RISCV\_TOOLCHAIN\_DIR}.
	\item Check the installation with \bashinline{riscv-none-elf-gcc --version}.
\end{enumerate}

Building the toolchain from source is an alternative when a specific version is needed. On Ubuntu or Linux Mint:

\begin{lstlisting}[language=bash]
sudo apt install autoconf automake autotools-dev curl libmpc-dev libmpfr-dev libgmp-dev gawk build-essential bison flex texinfo gperf libtool patchutils bc zlib1g-dev libexpat-dev
git clone --recursive https://github.com/riscv/riscv-gnu-toolchain
cd riscv-gnu-toolchain && mkdir build && cd build
../configure --with-arch=rv32imac_zba_zbb_zbc_zbs --prefix=/opt/riscv
sudo make
\end{lstlisting}

\noindent The tools are then installed under \texttt{/opt/riscv/bin} with the prefix \texttt{riscv32-unknown-elf-}; the commands below use the xPack prefix \texttt{riscv-none-elf-}, and the two are interchangeable.

\section{Compiling}

Each source file is compiled to an object file:

\begin{lstlisting}[language=bash]
riscv-none-elf-gcc -c \
  -march=rv32imac_zba_zbb_zbc_zbs \
  -mabi=ilp32 -O2 -Wall -Wextra \
  -I./include -g \
  main.c -o main.o
\end{lstlisting}

\begin{itemize}[itemsep=1pt]
	\item \bashinline{-march=...} names the extensions the compiler may use and must match this build's ISA string (Table~\ref{t:chip-config-derived}); the value above is the full VestaRV set. An extension can be omitted from the string for compatibility testing or size comparison.
	\item \bashinline{-mabi=ilp32} selects the integer calling convention of Table~\ref{t:cpu-registers}.
	\item \bashinline{-O2} is the recommended optimisation level; \bashinline{-Os} minimises size, \bashinline{-Og} favours debugging.
	\item \bashinline{-I} adds an include directory, such as the generated \texttt{MemoryMap.h} location.
	\item \bashinline{-g} keeps debugging symbols, which the disassembly listing and the debugger use.
\end{itemize}

The provided \texttt{start.S} must be the first object given to the linker: its first instruction is placed at \texttt{\SpiFlashProgramAddress}, the address the boot loader enters (Chapter~\ref{s:programming}), and it initialises the vector table and calls \texttt{main}. A C++ project declares \cinline{extern "C" int main()} so the entry symbol is not mangled, and may pass \bashinline{-fno-exceptions -fno-unwind-tables -fno-asynchronous-unwind-tables} to shrink or remove the \texttt{.eh\_frame} section.

\section{Linking}

The objects are linked with the provided linker script, which defines the ROM and RAM regions, the vector table, the entry address and the interrupt handler symbol from the generated fragments:

\begin{lstlisting}[language=bash]
riscv-none-elf-gcc -march=rv32imac_zba_zbb_zbc_zbs -mabi=ilp32 \
  -T MCU.ld -L linkerfiles_dir -Wl,-Map=program.map -g \
  start.o main.o -o program.elf
\end{lstlisting}

\begin{itemize}[itemsep=1pt]
	\item \bashinline{-T MCU.ld} names the linker script and \bashinline{-L} the directory of the fragments it includes (\texttt{memory.x}, \texttt{periph.x}).
	\item \bashinline{-Wl,-Map=} writes the map file with every symbol's address.
	\item \bashinline{-flto} enables link-time optimisation.
	\item \bashinline{-nostdlib} drops the C library; it also drops its software integer and floating-point routines and its initialisation code, so it is used only when size demands it.
\end{itemize}

\section{Loading the program}

An Intel hex file is produced from the ELF and written to the SPI flash through the ROM monitor by the provided script, which also switches the strap and resets the chip on boards that support it:

\begin{lstlisting}[language=bash]
riscv-none-elf-objcopy -O ihex program.elf program.hex
python3 forthprog.py program.hex --port /dev/ttyUSB0 --verify
\end{lstlisting}

\noindent The script needs the \texttt{IntelHex} Python package. Its \texttt{-{}-skipBlank} option skips erasing pages the image does not use, and \texttt{-{}-verify} reads the flash back after writing. The byte order and page handshake it implements are those of Chapter~\ref{s:programming}.
