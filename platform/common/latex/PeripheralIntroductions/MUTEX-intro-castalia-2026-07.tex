\section{Overview}

The hardware mutex bank (\peripheral{MUTEX}) provides \NumMutexesWord{} word-mapped advisory locks with single-instruction cross-hart mutual exclusion. A claim is one load and a release is one store; there is no reservation state and no retry loop in hardware. Atomicity comes from the multi-core arbiter, which serializes whole shared-window transactions, so two harts reading the same free mutex in the same cycle are still served one after the other.

\begin{itemize}
	\item \NumMutexes{} independent mutexes, one 32-bit word each (\register{MUTEX0} to \register{MUTEX15})
	\item Claim with one load: reading a free mutex returns 0 and claims it in the same transaction
	\item Reading a held mutex returns the owner's marker ($\mathrm{mhartid} + 1$) and leaves it held
	\item Release with one store of 0; any hart may release, so a supervisor can recover a dead hart's lock
	\item Nonzero writes are ignored, so ownership cannot be forged
	\item All mutexes reset to free
\end{itemize}

\section{Functional description}

\subsection{Claim and release}

Each mutex word holds either 0 (free) or the marker of the hart that holds it, $\mathrm{mhartid} + 1$. A read of a free mutex returns 0 and, in the same arbiter transaction, writes the reading hart's marker into the word; the arbiter attributes the read to the requesting hart, which is how the bank knows whose marker to store. A read of a held mutex returns the holder's marker and changes nothing, so a hart that reads its own mutex twice sees its own marker and is not disturbed. A store of 0 frees the mutex. The store is deliberately not qualified by owner, so that a supervising hart can release the mutex of a hart that has died while holding it; correct software releases only mutexes it holds. A store of any nonzero value is ignored, because the only legitimate nonzero content is a marker the hardware writes itself.

\subsection{Address decoding}

The bank occupies shared-window page 2 from \texttt{\MutexBaseAddress}, with mutex $n$ at \texttt{\MutexBaseAddress}${}+4n$. Only the low address bits are decoded, so the words alias throughout the page; software uses the canonical addresses.

\section{Interrupts and events}

Not applicable. The bank raises no interrupt; a hart that fails a claim retries under software control.

\section{Programming}

\subsection{Claiming mutex $n$}

\begin{enumerate}
	\item Load \register{MUTEXn} with a plain \asminline{lw}.
	\item If the value is 0, the mutex is held by this hart; otherwise the value is the holder's marker and the claim failed.
	\item On failure, delay by an amount proportional to $\mathrm{mhartid} + 1$ and repeat from step 1, with a bounded retry count.
\end{enumerate}

\subsection{Releasing mutex $n$}

\begin{enumerate}
	\item Store 0 to \register{MUTEXn} with a plain \asminline{sw}.
\end{enumerate}

\section{Usage notes}

\paragraph{Treat the locks as advisory.} The hardware does not block a hart that accesses a protected resource without claiming its mutex; the protocol is enforced by software only.

\paragraph{Never use \asminline{lr.w}, \asminline{sc.w} or an AMO on a mutex address.} A suppressed store-conditional reaches the bank as an ordinary read and claims the mutex, and an AMO performs a read and a write whose values the bank does not expect. Only \asminline{lw} and \asminline{sw} are legal (Section \ref{ss:multicore-sync}).

\paragraph{Back off between retries.} \NumHartsWord{} harts re-reading a contested mutex in lockstep waste arbiter bandwidth and can starve useful work; scale the delay with the hart index and bound the retry count.

\paragraph{Release only what this hart holds.} The bank does not check the releasing hart; a stray store of 0 frees another hart's lock silently.
